# Quick guide: from videos to model

How to use `sunnypilot.speedlimits` every day on the server (the LXC with the V100), with the three helpers and the web panel. To install the environment from scratch, see [INSTALL.md](INSTALL.md). For the `nnslr` commands one by one, see [upstream-training-guide.md](upstream-training-guide.md).

`nnslr` (Neural Network Speed Limit Recognition) is the name of the project and of its CLI (`.venv/bin/nnslr`): it recognizes speed limit signs with a neural network. The name comes from the project it was recovered from, `openpilot-nnslr-tools`.

Run every command from the repository folder, on the server:

```sh
cd ~/sunnypilot.speedlimits
```

Every operation below is a script of the repository: there are no manual steps to remember. If something is done often and is not a script yet, add it as a helper and document it here.

International sign units (runtime integrated locally on `speed-limits`, no deployment):
[plan](2026-11-02-speed-vision-units-plan.md) and
[verification report](2026-11-02-speed-vision-units-report.md).
`scripts/replay_speed_vision_country.py --help` describes the read-only local GPS
replay. It requires explicit border and experimental policy files; it downloads
nothing, runs no network inference, changes no review/dataset, and contacts no car.

## 1. The full loop

| Step | Command | What you do |
| --- | --- | --- |
| 0 | `helpers/fetch_comma_segments.sh` (on the site: the **comma** pill at the top right, with a green dot when the comma can be reached and accepts the server's key, then **Download new drives**; while it runs the pill shows its percent and bar, the drive it is at ("drive 44 of 46") and the segments downloaded; while a preparation or a code update runs it stays off and says what it waits for, since the two never run together. The comma's address is changed there too: it is saved in `data/web/comma.json` and passed as `--host`. For a new comma the panel walks you through the steps: SSH on and a GitHub user on the comma, the server's public key added to that GitHub user with **Copy**, the address, **Test now**; see docs/INSTALL.md, "The comma, from zero". A comma the server has already logged into once (the time of the last login is in `data/web/comma-seen.json`) and that is now only switched off shows "Last connected …" instead of the steps) | It downloads every drive still on the comma, also the old ones not in dashcam mode, into the folder shared with `openpilot.distill` (`/root/comma-videos`). It drops the first two and the last two segments, and those with the reverse gear; the first time a drive is downloaded they come too, marked `slow-only`, and only their pictures below 25 km/h are kept when the drive is prepared (a garage, a car park, the stop at a gate; the streets around the home are left out). Distill does not use them: it trains only on the drives it downloads itself (dashcam). |
| 1 | `helpers/1_prepare.sh` | Nothing: it links the videos, extracts the frames (1 per second, plus the exact frame of every sign the comma read) and proposes the signs for every new route. |
| 2 | `helpers/2_review.sh` | Open the link it prints, then confirm or correct the signs. It is the only manual step. |
| 3 | `helpers/3_train.sh` | Nothing: it imports the reviews, checks the dataset, freezes the split, creates `.venv-gpu` the first time and trains. |
| 4 | `scripts/publish_model.sh data/runs/<run>/bundle --no-upload` | Check the bundle. Then, without `--no-upload`, it publishes it on Hugging Face. |

At any time, `helpers/status.sh` shows every route (segments, frames, reviewed frames, objects in the dataset), what is running, the GPU and the disk, and the **next command** to run. It changes nothing.

You can run the helpers again whenever you like: work already done is skipped. `--help` on each one explains its options.

### Useful options

- `helpers/1_prepare.sh --jobs=4`: prepares 4 routes at a time (more cores, faster).
- `helpers/1_prepare.sh --background` and `helpers/3_train.sh --background`: they keep going even if you close the ssh session. The log is in `data/logs/`.
- `helpers/3_train.sh --dataset-only`: only the import and the dataset check, no GPU.
- `helpers/3_train.sh --continue`: a new training that starts from the "stable" weights published on Hugging Face.
- `helpers/3_train.sh --resume=<run>`: resumes an interrupted training (same folder `data/runs/<run>/`).

### Three rules to know

- **Training needs at least 3 reviewed routes.** `nnslr build-splits` divides the dataset into three independent parts, by whole routes: validation and test take about 15% each, and all the rest is train, so every reviewed route is used. The test takes first the routes with the most frames confirmed by a person (`--test-route <route>` puts a route in the test). With fewer than 3 routes it stops. The imported reviews stay in the dataset: nothing is lost.
- **The dataset follows the latest review of every frame.** A frame already imported and then reviewed again (boxes changed, or the review reclassified as AI) replaces its old rows. A frame already imported and then withdrawn is removed. The removed rows stay archived in `data/annotations/replaced/`. `nnslr import-annotations --from-db --dry-run` shows what would go in, what would be replaced and what would be removed, without writing anything.
- **A route already pre-annotated is never processed again.** A new pre-annotation would leave the reviews on the old report, and the import would skip them. Segments of that route that arrive later stay out; `helpers/status.sh` points them out.

## 2. The web panel

The site is in English and looks like `distill-web` and `perception-web` (dark; the **Account** icon at the top right opens the menu with the Dark / Light / Automatic look, the password and signing out). There are four sections in the top bar (on the phone, in a bar at the bottom, like an app): **Overview**; **Data**, with the pages **Drives** (`/prepare`), **Sign review** (`/routes`), **Drive review** (`/drive-review`), **Sign distance** (`/sign-distance`), **Roads** (`/roads`) and **Training dataset** (`/dataset`); **Training** (`/train`); **Models**, with **Versions** (`/models`), **Results** (`/evaluate`) and **Publish** (`/publish`). The pages of a section are under its title. It is one single page that switches tabs without reloading:

- **Overview** (`/`, the start page): at the top, the jobs running, one line each (percent, step, time left) with **Stop** beside it (a tap on the line opens the log), or the last job if it failed; then the loop of the work, four numbered cards in their order: **Drives** (the drives to prepare and who finds the signs, with **Prepare new drives**; with none, **Download** from the comma), **Sign review** (the frames left, in how many drives, the percent confirmed, with **Resume review**), **Train** (the reviews not in the dataset yet, with **Train all**, which opens Training › Pipeline; until 3 drives are reviewed, how many are) and **Car** (the networks in use that the comma's software does not have yet, with **Publish**, or **Finish publishing** while the build of psa-torque-sunny-testing is owed). Each title leads to its page; the first card with work waiting has a ring and the blue button; a job running for a card takes the place of its button (its **Stop** is in the list at the top); a card whose work is done has a tick. The cards are worked out from the data (drives, review, dataset, `models/active.json` and `models/on-car.json`), not from the sentence of `route_status`. At the bottom, the last three finished jobs (**Show all** for the others). The machine (GPU, CPU, RAM, disk), the processes on the GPU and **Update the site** are in the panel of the server pill at the top. The list of routes `/routes` (Data › Sign review) opens on a summary: the frames confirmed, by you and by the AI assistants, the AI's frames still to confirm, and one tile per group (In progress, To start, Done). A tile shows its list: one list at a time and always one, remembered in the browser, otherwise the first group that has drives.
- **Data** (`/prepare`, formerly "Prepare"): **Download from the comma** and **Prepare new drives**, their progress, and the table of the routes. **Find the signs → Found by** chooses who proposes the signs (Vietnamese YOLO, Our networks, Qwen3-VL) and shows its measure from Evaluate › Proposers (speed signs found and read right, seconds per frame). The choice stays on the server for every browser (`data/web/proposer.json`); until someone chooses, it is the proposer with the best measure. Every preparation takes it, also one started from the Overview's Drives card or with **Try again**, and `helpers/1_prepare.sh` from a terminal without `NNSLR_PROPOSER` (the Vietnamese YOLO only before any choice). With Our networks chosen, the line under it names the cutter, classifier and applicability network in use (**In use now: cutter SignNet, 30 Oct 10:46 · …**, changed in Models); the Overview's Drives card says it too (**Found by Our networks: …**, with **Change**). While a preparation of the site is running, it shows that preparation's proposer and cannot be changed; its card says it too, with Our networks' cutter, classifier and applicability network (those in use when it started). With a SignNet in use, Our networks see only the band at the top of the frame, as the car does: a sign lower down (a road marking, a low sign close by) is not proposed. With Qwen3-VL not installed, or with less than about 18 GB free on the GPU, **Prepare new drives** and **Propose again** stay off, with the reason. Without new routes the page points to the comma's **Download new drives** in the top bar.
- **Results** (`/evaluate`): **Drive**, the first view, replays a drive as in the car. It shows the real video of the comma's road camera (20 frames per second; the server converts it to MP4 the first time Drive shows the drive, on the GPU, about a minute for a 45-minute drive, or on the CPU when the GPU's memory is taken, with `nnslr drive-video`, and meanwhile it shows the frames, one per second, with how much is left). On the frame are the speed signs the networks read (green: right; orange: another number; red: where there is no sign; dashed: the missed ones), and in the corner the limit the car would show now, next to the limit of the reviewed signs. Below is the strip of the drive, green where the limit is right and red where it is wrong (a tap goes there), and at the side the percent of the drive with the right limit. The limit is the last sign read, held until the next one or an end of limit: a single sign read wrong stays until another one is read, as the car would do. The road a sign applies to (applicability) is not there yet: every sign read counts. You choose the drive, the **Networks** (a pair: a classifier and the cutter it was measured with at the end of its training; the line under the choice names both, and **In use** marks the pair whose two networks are both in use) and **Test drives** (roads the networks never saw in training: how they would do on a new road) or **Validation drives** (used during training to choose when to stop, so a bit easier). **Scores** has the numbers of every version, per network (Proposers, Chain, Cutter, Classifier, Applicability, AI reviewers): two versions are compared only when they were measured the same way on the same test.
- **Models** (`/models`): at the top, the networks in use (cutter, classifier, applicability, scene) with their numbers. Below, the versions of one of them (the switch, or a tap on its card) in a table to compare: only the recent ones (the one in use and the others of its training, the newer ones that can be put in use, the one on the car or tried on the comma, a training running now; with none in use, all those that can be), the others behind **Show N older versions** (nothing is deleted, the files stay) (speed signs, all signs, and for the classifier the chain with the cutter; under each number, how many signs it is measured on). A row opens its card, with **Use this one**. The cutter is SignNet (`nnslr train-signnet`, the network the comma runs: the 896 × 288 band at the top of the frame, stride 8); the one in use gives the boxes of Prepare's Our networks, of the classifier's false boxes and of the chain: the car's best 5 boxes a frame, from score 0.1 (the car keeps those of 0.3 or more); the chain is judged at 0.3, as the car reads it. **Use this one** is there only for a finished SignNet that fits the car (band 896 × 288, stride 8); a SignNet with another band, or an unfinished one, says why it cannot be chosen. The old Detectors (`scripts/run_detector_sizes.sh`, the detector of a whole pipeline) stay among the older versions to compare, and cannot be put in use; one already in `models/active.json` stays in use until a SignNet is chosen. **Speed signs** and **Every sign** count the signs found at threshold 0.1, with all the boxes that pass (a Detector has a couple of hundred per frame, SignNet a few). **In 5 boxes** counts the speed signs among the 5 best boxes of every frame at any score ("–" for old reports that do not keep the boxes of every frame); the car reads fewer, only the boxes of score 0.3 or more: on the test of 26 October the SignNet on the car finds 152 of the 381 signs (40%) and 120 of the 208 speed signs (58%) at 0.3, with 0.22 false boxes a frame, against 209 (55%) and 130 (62%) among its best 5 boxes at any score. **On the car** marks the networks the comma downloads (the SignNet, the classifier and the scene network published in `speed-limits-models`). Each card at the top says whether the version in use is that one: **On the car: this one** in green, **On the car: an older one, 28 Oct 11:15** in orange (two versions often have the same name: the time tells them apart), with what puts it there (**Publish**, on the Publish tab); applicability runs only on this server. A trial on the comma shows instead as **On the comma: … as a trial**. `nnslr on-car` records them (section 6) in `data/models/on-car.json`; they do not change the networks in use. A training of the scene network gives two versions, **With memory** and **Without memory**: the table has the share of the first minute after a ramp said motorway, the macro F1 of the road types and the F1 of the town; the card adds the F1 of each road type on validation and test, the changes found (merge, ramp, town entry and exit) with their delay, the false switches per hour and the size of the network. Since the third version it also has the junction head: the table has **Junctions**, the F1 of "passed" within 2 s on test with the false "passed" per hour under it (a false "passed" lifts a sign's limit, the dangerous error; on a phone the column is left out, the card has it); the card adds a **Junctions** table on validation and test (passed, F1 at 2 s and recall at 4 s, false per hour and per 10 km, in town and outside) and how many test junctions came after a number sign. Since the fourth version the card also says the inputs (the speed from `carState.vEgo` or the GPS, the sign, the car's motion: its turn, steering wheel and blinkers) and whether the junction head has a memory of its own, with its epoch; the junction table ends with **Turn alone**, the car's turn as a plain rule (a heading change of at least 60° on a radius of at most 40 m), to show what the network adds to it. The scene network in use goes to the comma with **Publish**; the comma runs it once a second (`speedvisiond`). **Publish** (`/publish`) puts the networks in use into the comma's software in one go, with one button, **Publish** (`scripts/send_to_car.sh`): the SignNet, the classifier and the scene network in use are prepared as ONNX and checked, published in `speed-limits-models`, the sunnypilot `speed-limits` branch moves to them and `psa-torque-sunny-testing` is built again (a few minutes; its five steps show in place of the button). Then, on the comma: Settings, Software, Check for updates, and install. Above the button, each network in use next to the one the comma's software has (**On the car: this one** in green, **an older one** in orange); the button is there only while one differs, or a build is still owed (**Finish publishing**), and only for a finished SignNet that fits the car (a band of 896 × 288, stride 8). Below, apart and optional, **Hugging Face**: a package of the cutter, classifier and applicability in use for other people (**Prepare the package**, then **Publish on Hugging Face**); the car does not need it.
- **Regression** (`/regression`, Models › Regression): to test any model on drives you know went well. **Certify a drive** picks them once, and they stay. **Models** lights what to compare: **Small** (CD210, `stock`), **Big** (MD v3, `teacher`), **In the car** (the plan the comma logged), the runs of `openpilot.distill` (**Distilled** and their date) and the versions of the brain (**Smartspeed**). **Run** computes on the GPU only what is missing on the certified drives, so after a training only the new model runs; it trains nothing and changes nothing on the car. Each certified drive says what is ready and how much of it the models trained on, where the test is not fair. A tap opens it (`/regression?drive=<route>`): the player of Drive review with the lane **Models**, your speed and a curve per model lit. At the side, each model's speed at the time shown, how far it stays from your speed over the drive, and a tap turns its curve on or off. **With Smartspeed** is the lower of a model and the first brain lit: the car's speed with our cap. **2 s, 5 s, 10 s** choose how far ahead the plan looks; the value is drawn on the moment it speaks of.
  It is open loop: the car drove as you drove, each curve is what a model would have said looking at that video, not what the car would have done. A model close to your speed followed the traffic you were in; only a road test says how it drives. The driving models need the wide camera (`ecamera.hevc`): a drive without it runs only In the car, and the brains need a prepared drive. The results stay in `data/regression/results/<route>/`, one file per model; the certified drives in `data/regression/routes.json`. Removing a drive keeps its results.
- **Publish** (Publish tab) and **Try on the comma now** (on the card of a SignNet, Models › Versions, Cutter): Publish takes the SignNet in use, Try on the comma now that SignNet; both take the classifier in use, and ask first; both refuse, before starting, a SignNet that does not fit the car (a band other than 896 × 288 or a stride other than 8) or has not finished; Publish also takes the scene network in use (with memory), whose road type gives the limit where no sign does (a garage 10, a car park 20, a town 50), and drops the published one when none is in use, while Try on the comma now keeps the build's. **Publish** (`scripts/send_to_car.sh`) publishes them in `speed-limits-models`, moves the sunnypilot `speed-limits` branch to them and builds `psa-torque-sunny-testing` again (a few minutes; nothing is published or built when they are already there); then, on the comma: Settings, Software, Check for updates, and install. **Try on the comma now** (`scripts/try_on_comma.sh`) copies them straight onto the comma over ssh, without publishing or building: they last until the comma's next software update. Before copying it checks the comma (it answers, it is parked, its build has speedvisiond, Show Vision Speed Limit is on or Speed Limit Source is Map Data + Vision or Vision Only) and the networks with the comma's own code (their contracts against its `vision.py`, then its `read_signs` on 5 reviewed frames, the confirmed speed read on 3 at least); then it waits up to 6 minutes for the parked comma to compile them, and puts the build's networks back itself when it does not. While a trial is on, the Models tab marks the SignNet **Trying on the comma** and shows **Back to the build's networks**. Its button is off, with the reason, when the comma does not answer on the network (checked at most once a minute). Its job shows at the top of the Models page while it runs, Publish's on the Publish tab. With nothing to publish the button reads **Build again**: the networks stay, `psa-torque-sunny-testing` is built once more (`--rebuild`), for code changed on `speed-limits`. The card shows only jobs of this button: a failed one finished from a terminal reads "failed, finished later".
- **On the car** (Models › Versions, last card): the settings of the comma's vision limit, the constants of sunnypilot's `speed_limits/vision.py` (how sure a sign must be and in how many pictures, how long a road type must be seen before its limit counts, how long a road must be seen to leave a car park (3 s), how sure a 30 zone must be, the limit of a car park in the open (20) and of a garage (10), a ramp's seconds; under **Sign distance**, how much shorter the distance to the sign ahead is shown (0.34 s of the speed and 6.8 m, measured in Data › Sign distance) and how wide a gantry's LED limit is (1.4 m)). **Save** keeps them in `data/models/car-settings.json` (only those changed from the default); they reach the comma with the next **Publish** or **Try on the comma now**, in the `settings` of `speed_limits.json`, never on their own. The card says whether the comma has them already. The comma takes each one within its bounds and keeps its own default for the rest.
- **Drive review** (`/drive-review`): to see what happened in the car, over whole recorded drives rather than single frames. It joins the drive's video to the comma's own logs (what the car saw and did: its vision limit, the map's limit, the resolver, Speed Limit Assist, openpilot's state, the pedals, the steering wheel and the set speed) and lists the **episodes** worth a look: the driver stepping in while openpilot drove (accelerator, brake, the wheel held, a disengagement, a set speed changed by hand), and the comma's vision limit and the map's 5 km/h or more apart for 3 s or more. The vision reads a sign tens of metres before the car reaches it, while the map changes only where its limit begins, at its next update: when the vision changed first and the map came to the same limit within 10 s, the vision was ahead, not wrong, and no episode is made. The scan reads the logs only, on the CPU (no picture, no network, no GPU), and runs when you press **Look on the server** (one drive) or **Look for episodes in every drive** (all of them); `nnslr drive-review scan --all` does the same from the shell. **Drives from** (next to the count of drives searched) is the first day reviewed, 30 Oct 2026 by default: the drives before it are not searched and their episodes stay out of the list, because the vision network on the car was not yet the one to judge (empty: every drive). The logs come from the comma's download (`helpers/fetch_comma_segments.sh` already copies the rlog of every segment) or from the page: **Send a folder of logs** (the comma's own folders `<drive>--<segment>/rlog.zst`) and **Send log files** (named `<drive>--<segment>--rlog.zst`, as comma connect downloads them). Sent logs are kept unchanged in `data/raw/drive_logs/` with their SHA-256: sending the same file twice keeps it once, and a scan reads again only what is new. A drive without logs says *Logs not available: import the logs to look for the episodes of the recorded drive.* and its video plays all the same; one whose logs are on the server but cannot be opened by it says *Logs found, but this server cannot open them (their file permissions)*, and is not searched again until they can be opened (the count of drives to search, Search all, the drive's own button and Sign distance follow the same rule). The queue puts first the episodes whose clues agree (with the reasons), says when each one was (≈ when the logs have no GPS fix and the time comes from the videos), and filters by drive, kind and data available. An episode opens on the video with the comma's lanes under it (vision, the signs it read with the reason its limit holds, map, resolver, speed with the set speed and the target, openpilot, scene; what our networks find on the server today and the map as it is today in separate lanes, never mixed with what the comma recorded), from 30 s before; the zoom goes from the episode to the whole drive, **Last limit change** jumps to where the vision limit last changed, and space, ← and → (⇧ for 10 s) move the video. A hatched lane is a stretch the logs do not have. Nothing is judged here and nothing is saved: the page only shows, and the signs are reviewed in Sign review. **Review the signs here** opens Sign review on the frame nearest the moment shown (with every frame listed, so a confirmed one opens too), and every frame in Sign review has **What the car did here, in Drive review →**, which opens the drive 2 s before that frame. When the drive's logs are scanned, a bar above the photo (never on it) shows the flag of the frame's country (from the GPS) and what the comma had at that frame (km/h): **Map** (with the limit ahead and its distance), **Vision** (the limit its memory held, with *sign in N m*, how far it saw the sign, when the car's build logs it: speedVisionSP.signDistance, empty in the drives of Oct 2026) and **Car** (the limit the car used, "from vision" or "from map"), outlined in red when map and vision are 5 km/h or more apart; in the timeline those frames have a red dash under their tick (*map ≠ vision in the car*). Between the frames at 1 a second, Sign review also has the exact frame of every sign the comma's vision read (the first read of each sign, from the drive's logs; `nnslr sign-reads <route>`, run by Prepare before proposing, and by **Propose again**, which keeps the confirmed frames): the bar above the photo says *The comma read 20 here*, its time has hundredths (19:32.85) and in the timeline it is a thin blue bar in the cell of its second, as far into it as the frame is (*a sign the comma read*). Its key is `<segment>/<1000 + frame of the video>`, so the frames at 1 a second and their reviews never move; the road types, the junctions and the networks with memory keep to the frames at 1 a second. It is read from the car's logs, never from the map as it is today. In Sign review ← and → (‹ › on the phone) go through every frame of the video, 20 a second, and ⇧ ← → (« » on screen) a whole cell, from second to second; the cells of the timeline stay one per second, and the frame of the video on screen is an empty bar ringed in its second. Where the server has the segment's video, a cell is green when every frame Confirm goes through in its second (below) is confirmed; until then it fills from the bottom as far as they are (*partly confirmed*). A second whose picture is confirmed with no sign is green at once. The green is only the page's progress: every confirmed frame goes into the dataset on its own, so a second partly confirmed loses nothing. The line under the photo says which frame of its second is on screen (*4:22 into the drive · frame 7/20*). The server decodes these frames on demand, a GOP (20 frames) at a time, into `data/derived/video_cache/` (at most 1 GB, the frames shown least recently deleted first). Confirm works on these frames too, with their boxes or as *no sign*. With **To review** or **All**, Confirm goes on frame by frame through the video while the frames have a sign (with To review, over the frames already confirmed); after a frame confirmed with no sign it skips the frames not saved and goes on to the next frame of the report (a sign the comma read, a frame already saved) or the picture of the next second; » still skips a whole second. **Apply previous** (A) and **Fit box** (C) work on them too: A carries the boxes of the frame just before, each one to check (the frame has no proposals to move it onto), and C fits them, so A, C, Enter goes quickly through the frames of a sign. **Ask AI** and **Fit with AI** work only on the frames of the report (the pictures at 1 a second, the comma reads and the frames already saved). Saved, it gets its own picture (`video_<1000 + frame>.png` in the segment's frames, listed in `video_frames.jsonl`) and the key `<segment>/<1000 + frame of the video>`, like a comma read, so the frames at 1 a second and their reviews never move; from then on it is a frame of the report like the others, counted in the cell of its second: **Propose again** keeps it and the import puts it in the dataset. An episode takes the colour of its kind on the strip of the drive and in the **Episodes** lane: orange vision against map, blue an intervention, red both. The browser keeps a drive's video for a day, so going back in it plays at once; a slow network still shows as pauses while it loads. An episode keeps its id across new logs, new scans and new scanners, so a link to it still opens it. What the logs can and cannot tell is in [DRIVE_REVIEW_AUDIT.md](DRIVE_REVIEW_AUDIT.md).
- **Speed review** (`/speed-review`): to say the speed the car should really hold, stretch by stretch of a drive. These labels are the target the brain network will learn from: the limit in the logs cannot be it, it holds the very errors to remove. Nothing here changes the car and nothing trains. The list shows every drive, the newest first, each with how much of it is examined; the five to review first say so (`00000160`, `0000015a`, `00000154`, `00000151`, `00000153`: 169 minutes that hold 93% of the suspect seconds and the roadworks). The test drive `0000012d` is the last to review: its logs have no vision limit to propose from.
  A tap opens the player of Drive review (`/speed-review?drive=<route>`, **‹ Speed review** to go back) at the first stretch nobody looked at, with one lane more on top, **To hold**. The proposal is the limit the comma's vision held, in stretches rounded to 5 km/h, a stretch under 5 s joined to the one before. On free road it is your own speed instead: no car ahead, no curve on the GPS track, the speed steady for 15 s, and the proposal is the nearest limit (78 km/h held proposes 80; the card says **your steady speed on a free road**). Anywhere else the vision limit stays. The map is never a proposal. Dashed: nobody looked at it, and a proposal left alone never counts as approved. Green: confirmed. Blue: corrected. **?**: you looked and nobody can tell.
  The question is always the same: which cap would you set here on a free road, leaving queues, curves and stops to the planner? **Yes, 80** (key y) confirms the stretch and goes to the next open one. **−5**, **+5** (keys − and +) and the numbers correct it. **?** says nobody can tell and goes on. In a stuck limit the right change is inside the stretch: stop where it should change, press **Split here** (key s) and answer for one half. The cut is real once a half is saved; **Remove split** takes it away before that. A drop starts where the sign can be read, a raise at the sign.
  On a saved stretch, **Known from here** marks from when the past is enough to work the speed out (a missed end of a limit starts at the sign nobody saw, and shows only further on), **Clear** puts it back to not examined, and a note stays with it. **1× 2× 4×** set the speed of the playback. Every command saves at once. Two tabs cannot overwrite each other: the second one is told and reads the drive again. Only a person signed in writes here: no MCP tool, no REST write, no command.

## 3. The always-on site: the `speedlimits-web` service

To keep the site and the panel always on, even after a restart of the server, install the systemd service once (as root):

```sh
cd ~/sunnypilot.speedlimits
helpers/2_review.sh --stop                        # if you had started the review by hand (port 8765)
scripts/install_review_service.sh --dry-run       # shows what it would do, changes nothing
scripts/install_review_service.sh                 # installs, starts and prints the link
```

The service listens on `0.0.0.0:8765`. It restarts by itself if it stops, and at every boot. Running the install again does no harm: it rewrites the service only when `deploy/speedlimits-web.service` changed, and it does not touch the token.

### Signing in from the browser: name and password

On the LAN the site asks you to sign in with a **name and password** (pages, panel and images). The **first visit** creates the administrator: the page asks for the **setup code**, which is the server's access token, then for the name and the password (at least 12 characters). From then on the token no longer opens the site in the browser: it is only the key of the `/api/v1` API, of MCP and of the agents that send it in the `X-Review-Token` header.

- The **Account** page (at the top) shows who is signed in, signs you out (also from every browser) and changes the password. After the change, the other browsers have to sign in again.
- A session lasts 7 days without use, 30 days in all. 5 wrong attempts from one address block it for 15 minutes.
- The sign-in files are in the data folder, under `web/auth/` (`admin.json`, `sessions.json`, permissions 600; the password is saved only as a scrypt hash).
- **Forgotten password**: on the server, in the folder of the clone, run `helpers/reset_password.sh`. It stops the site, moves `web/auth/admin.json` of the data folder to `admin.json.<time>.old` and starts the site again (the service, or the site started by `helpers/2_review.sh`). The next visit asks again for the setup code, then for a new name and password. Reviews and settings stay; every browser has to sign in again. The sign-in page mentions it under **Forgot the password?**.
- Old links with `?token=...` no longer open the site: they lead to the sign-in page.
- Started by hand only on `127.0.0.1` (without `--host 0.0.0.0`), the site stays open to this computer without signing in, as before.

### The token (setup code and API key)

The place to look for it is the **`.env` file of the repository** (`~/sunnypilot.speedlimits/.env`), the line `NNSLR_REVIEW_TOKEN=...`:

```sh
grep NNSLR_REVIEW_TOKEN ~/sunnypilot.speedlimits/.env
```

- `.env` is in `.gitignore`: it never ends up in git or on GitHub. It has permissions 600 (only root reads it).
- Whichever needs it first creates it: `helpers/2_review.sh` or `scripts/install_review_service.sh`. The install of the service uses the token already in `.env`; if there is none, it creates one and writes it in `.env`.
- The systemd service reads it from its own copy, `/etc/speedlimits-web.env` (permissions 600). Every install writes the same value back into `.env`.
- The install, `helpers/2_review.sh` and `helpers/update.sh` print the address of the site (`http://<server IP>:8765/`), without the token.

Do not share the token: whoever has it can create the administrator while there is none, and can use the API. To change it, write the new value (at least 16 characters, from letters, digits, `-` and `_`) in `/etc/speedlimits-web.env`, then run `scripts/install_review_service.sh` (it copies the value into `.env`) and `systemctl restart speedlimits-web`.

### Updating the code

```sh
cd ~/sunnypilot.speedlimits
helpers/update.sh
```

`helpers/update.sh` runs `git pull --ff-only` (it stops when there are local changes), updates `.venv` when `pyproject.toml` changed, runs `scripts/install_review_service.sh` again (it rewrites the service only when it changed) and restarts the service. Without the service, it restarts the site started by `helpers/2_review.sh`. At the end it prints the link, except with `--no-link`: that is how the **Update the site** button runs it, in the server panel (the GPU/CPU pill at the top right). The button is off, with the reason, while a job runs that the update cannot interrupt. After the confirmation, the site follows the job and reloads the page only when it succeeded; otherwise it writes "Not updated." and why (in the panel and in a notice at the bottom).

The service has `KillMode=process`: a restart stops only the site, not a preparation or a training started from the panel. After the restart the panel finds them again as "running".

### Checking and stopping

```sh
systemctl status speedlimits-web                     # is it on? since when?
journalctl -u speedlimits-web -n 50                  # the last lines of the server (also "Pannello: avviata ...")
systemctl stop speedlimits-web                       # switches it off (it starts again at the next boot)
scripts/install_review_service.sh --uninstall     # removes the service (the token stays)
```

### REST API and MCP (review without a browser)

The same service also offers the **REST API** (`/api/v1/...`) and, with the optional MCP dependencies, the **MCP** server on `/mcp`, to review with `curl`, a script or an AI (Claude Code, Codex) that runs on its own computer. Everything is in [API_MCP.md](API_MCP.md). In short:

- the token goes **in the header** `Authorization: Bearer <NNSLR_REVIEW_TOKEN>`, never in the address; it is needed on 127.0.0.1 too;
- the same rules and the same database as the page; the panel (Prepare, Import, Train, Update) cannot be reached from the API or MCP;
- install the MCP dependencies once and restart the site: `helpers/setup_mcp.sh --restart` (see "Local install for MCP" below);
- MCP also works without HTTP, over ssh: `helpers/mcp.sh` (with `--read-only` for a trial without saving; `NNSLR_MCP_READ_ONLY=1` in the service does the same on `/mcp`);
- the reviews of an AI are saved as `ai/<name>`, type `ai`, and they do not change the confirmations of a person. They are final, like those of a person: `helpers/3_train.sh` imports them into the dataset without another approval, with the AI provenance (`ai/<name>`, `label_basis` `ai_review`, channel). Confirming does not import and does not train: import and training are started separately.

#### Local install for MCP

Some things are not in git, because they are installs or settings of the machine. `helpers/setup_mcp.sh` does all of them. You can run it again whenever you like (it skips what is already there):


| --- | --- | --- |
| MCP SDK (`mcp` 2.x and its dependencies) | `.venv` | installed packages |
| MCP server `nnslr-review` (stdio, `helpers/mcp.sh`) for Claude Code | `~/.claude.json`, for the folder of the repository | Claude Code configuration of the machine |
| `mcp__nnslr-review` tools allowed without asking, `effortLevel` of the sessions | `.claude/settings.local.json`, listed in `.git/info/exclude` | a local setting: the review sessions started here (also the remote ones of the bridge environment) do not stop to ask, and do not use the high effort |

To take the permissions away from the sessions, delete `.claude/settings.local.json`. To remove the MCP server: `claude mcp remove -s local nnslr-review`.

Reviews an AI made from the page (with a name like `Codex` or `ChatGPT`) count as human. `nnslr review-reclassify-ai --reviewer Codex --reviewer ChatGPT --dry-run` counts the ones to change; without `--dry-run` it marks them as AI (a new review in the history, same boxes). Make a copy of the database first.

The review database updates itself to version 2 at the first start of the new code (it adds the reviewer type and the channel; the reviews already made stay "human, from the page"). After that, an old `nnslr` can no longer open it.

### Fitting a box (C and ⇧C)

On the review page a rough box is fitted to the sign under it in two ways:

- **Fit box** (key **C**, and the chip under the sharp crop of the selected box; **Apply previous** does it by itself on the boxes it carries): **C** fits every box of the frame, whichever is selected (after **Apply previous**, after **Apply** of the AI, a box just drawn), except the boxes you moved or resized by hand since a fit last moved them, which stay where you put them; the chip fits only its own box, by hand or not. The server's CPU fits them in one request and well under a second, with no AI provider (`nnslr_tools.box_fit`: colour masks and grabCut ranked by a small tree model, edge and MSER candidates ranked by three tiny networks, their mean pulled back toward your box as far as it already agrees with it). On drives left out of the training of its weights it takes a rough box from a mean IoU of about 0.64 with the box a person drew to about 0.78 (the two constants of the mean and the pull-back were chosen once on boxes from the same drives, so the figure is a little optimistic). When it finds no better box (no sign there, or your box already right) or moves no side by a pixel, it says "No better box found: kept as it was" and leaves the box, and the frame, as they are. A fitted box is an unsaved change, saved only by your **Confirm**.
- **Fit with AI** (**Shift+C**, the chip beside it): the AI reviewer of Settings fits the selected box, or every box of the frame when none is selected, one at a time. It is slower and needs a provider that passed its Test; use it when **Fit box** misses.

Neither moves a box with **Panel below** on **Hours**: it holds the disc and the plate, and both fits look for the disc. The page says "The box takes the disc and the plate: kept as it is."

Both work only for a browser that has signed in, or the site on 127.0.0.1; the token alone cannot fit boxes. At most two fits run at a time. The models are `src/nnslr_tools/box_fit/colour.npz` and `edges.npz`: `scripts/train_box_fit.sh` trains them again on every box people drew (CPU only, about 15 minutes), and the site uses them after its next restart.

### What the classifier gets

Beside the zoom of the selected box, the square **Classifier** shows that box as the network gets it: cut from the frame and stretched to 160 × 160, its proportions lost, each of its pixels one the network gets. Under it, how many pixels of the frame that is. It is made in the page from the photo on screen, so it follows a corner being dragged. That photo is the preview, a JPEG of the same size as the frame: measured on three signs, the square is 1 to 4 levels of 255 off the network's picture on average, most on the smallest sign. On a drive at full definition the preview is the frame as recorded, so the square and its pixels are those of the 2688 × 1520 frame: a box 60 wide reads 120. It saves nothing.

### A limit with hours (Panel below: Hours)

A 30 with a plate of hours under it is another sign for the classifier: "Speed limit 30, with hours", the class `maximum_speed_hours:30`. In **Sign review** choose **Speed limit**, its number and **Panel below › Hours**, and draw one box around the disc and the plate; the page says so under the row. When the plate can be read, set **From** and **To** under it: whole hours, saved with the sign, and the class becomes `maximum_speed_hours:30:22-6`, so that the car and the brain know them. Leave them empty for a plate too small to read, or one with days, minutes or two ranges. Hours with fewer than 3 crops of train stay in `maximum_speed_hours:30`. A limit with hours and no readable number stays a limit with no number. **Apply previous** carries such a box with its shape and its hours: a box of the disc alone it finds there is taken down over the plate, to check. A plain number that the cutter finds closer with **Hours** keeps **Hours**. **None** and **Other** keep the box on the disc.

To reach the car, in this order:

1. Mark the signs in **Sign review**.
2. **Import the reviews.**
3. **Train the cutter**: the car's classifier sees only the box SignNet cuts, so SignNet has to learn the tall box too. Choose it on **Models**: the classifier learns the false boxes of the cutter in use (Train › Pipeline does steps 2 to 4 in a row, with the new cutter).
4. **Train the classifier**: it gets one class for each number with hours, and one for each number with hours read. The hours need drives at full definition to be read on the car: at 1344 × 760 the plate is a blob.
5. On **Models** choose the classifier, then **Publish**. The brain reads the drives with the networks of the release, so a brain trained before this Publish has never seen the new class.
6. **Train the brain**: it reads the labelled drives again first. Models › Brain then says **Reads them** under **Hours plates**, if frames of train with a speed labelled had a plate, and **Reads them and their hours** if they had their hours read.
7. Choose a seed on **Models** and **Publish** again.

With no Hours label nothing changes: no such class, and the same classes as today.

### Drives at full definition

A comma with **Record road at full resolution** on (Developer tab) writes its `fcamera.hevc` at 2688 × 1520 instead of 1344 × 760. The server tells them apart by the size of the video when it extracts the frames, drive by drive, with no setting; old and new drives live side by side. Such a drive says **HD** beside its date.

- **Rows, boxes and labels stay in 1344 × 760 pixels**, on every drive. Each picture `frame_XXXXXXXX.png` is the recorded frame reduced by 2, and the recorded frame stays beside it as `frame_XXXXXXXX.full.jpg`. So the cutter, the reviews already saved and the dataset do not change.
- **Sign review** shows the recorded frame, in the photo, the zoom and the **Classifier** square. Drive review plays a video as wide as the recording.
- **Training** cuts the classifier's crops from the `.full.jpg` when a frame has one, by itself, and the crop cache is rebuilt for those frames (`meta.json` and the log say `full_frames`). Frames without one keep their crops. A classifier trained before those drives is not changed: training stays your choice.
- **What it costs:** about 4.5 GB an hour on the comma instead of 2.25, and on the server one more JPEG for each picture, with a preview of the full size. `deleter.py` removes the oldest segments when the comma has under 10 % or 5 GB free, so pull a full drive within days.

With either switch on the road camera goes through the BPS, the comma's other image processor, and that also changes the picture the driving model sees: another debayer, no vignetting correction, about 7 ms later. Both off, everything is as before. A change applies from the next drive.

The road through the BPS has not run on a comma yet: the code is read and compiled, the picture is not seen. So the first time, turn a switch on with the car parked and the ignition on for a few minutes, download that drive from the **comma** pill and look at it in Sign review: right colours, no seams down the picture. Only then drive with it.

### The car's networks on a frame (T)

In Sign review on a computer, the short bar between the photo and the bar under it is a grip: drag it up and the photo gets lower, the timeline under it gets the room; drag it down and it grows back, at most to the width of the column. With the grip focused, ↑ and ↓ move it (⇧ in bigger steps); a double click goes back to the default height. The browser remembers the height. The bar under the photo has two rows: the frame (‹ ›), the filters and **Car networks** / **Ask AI** on the first; the frame's state, the frame data and **+ Box** / **Delete** on the second. On a tablet or a phone the page scrolls instead and there is no grip.

In Sign review, **Car networks** (key **T**, its button in the bar under the photo, next to **Ask AI**) shows what the car's own networks read on the frame on screen: SignNet (the cutter) finds the boxes and the classifier reads each one, run by the car's own code (`vision.read_signs` of the sunnypilot clone, `NNSLR_SUNNYPILOT_CLONE` or `/root/sunnypilot`) with the networks and the settings of the release the car runs (`models/speed_limits.json`). It works on any frame: a picture at 1 a second, a sign the comma read, or any frame of the video between them (← →). Once on, it reads every frame shown until its button (or **T**) is pressed again; the browser remembers the choice. On a frame not confirmed each box of the car goes straight into **Signs** on the right, with its kind, value and whom it is for, in fuchsia on the photo: fuchsia means found by the car's networks, and it stays fuchsia once confirmed. Their row says *car networks*. There is no button to press: check them and **Confirm** as always; nothing is saved before that, and a frame only passed over stays to review, without them. **Not a sign** boxes come too: most are false boxes of the cutter, and confirmed as they are they are examples of not a sign, so on a real sign change the kind, on a false box leave or delete it. A box deleted there does not come back while the page is open, and no box is added where the frame already has one. Whom a box is for (*OURS*) comes from the applicability network in use (Models tab), which is not on the car: it runs here on the CPU (`nnslr_tools._decider_worker`, in `.venv-gpu`, loaded at the first frame, about 4 s, then 0.1 s a frame, and gone after 10 idle minutes), with the car's speed at that frame. It answers on every box but those read as not a sign. It learnt only on the speed families (limits, ends, zones, variable displays, road markings), so on any other sign its answer is only a hint to check. If it cannot answer, a card under the bar says why and the reading stays good. On a confirmed frame the car's boxes are only drawn, in fuchsia (*car 1 · 80 · 97%*), and listed in that card with what the classifier read, how sure it is and what the car does with it: **Limit 80** (or **Ends the limit**) goes to the car's memory; **Road type** and **Board, road type** go to the road type; **No limit** is read sure enough but holds no limit (another sign, not a sign); **Dropped** is under the release's minimum confidence (70 % today), and the car ignores it. On the photo a dashed box gives nothing for the limit and a dotted one is dropped.

It is close to the car, not bit for bit: the car reads the camera's frame before the video encoder, with tinygrad on its GPU, while the server reads the recorded video (`fcamera.hevc`, decoded to the camera's NV12) with onnxruntime on its CPU, so a confidence near 70 % can fall on the other side. One frame is not a limit either: the car's memory takes a number read in 2 frames within 1.5 s. Only the camera, never the map. The first frame of a GOP takes about half a second (the server decodes its 20 frames), the next ones of the same GOP a few hundredths. A new release in the sunnypilot clone is used from the next frame read, without a restart; with no release there, the box says so (503).

### The AI reviewer (Settings)

A review can be done by hand, or by an AI that sees the images, through any server compatible with the OpenAI API (`/v1/models` and `/v1/chat/completions`): strata, your own llama.cpp `llama-server` on another machine with a vision model and its `--mmproj` file (for example Qwen3-VL-32B-Instruct), or another service.

- **Connecting a provider**: menu **Account → Settings**, the **AI reviewer** box: a name, an address that ends in `/v1`, the API key (when the server wants one) and the model (the list comes from the server; when it does not answer, type it by hand). **Test** sends a frame reviewed by a person, without the proposals, and says whether the model answers in JSON and reads the speed sign. When the server says the model takes text only, it says so without asking the model anything. Below, **Who reviews** is a list with a check mark: choose a provider that passed the Test, or **Don't use AI**. A provider never tested, or one that did not pass its last Test, cannot be chosen (not from the terminal either). When the chosen reviewer no longer passes it, **Ask AI** and **Review with AI** stay off, with the reason, until it passes again. Changing the address or the model clears the Test.
- **From the terminal**, for example strata:

  ```sh
  .venv/bin/nnslr llm-provider add --name strata --base-url https://strata.farm.14bodhi.com/v1 --key-file /root/.config/strata-api-key
  .venv/bin/nnslr llm-provider test strata
  .venv/bin/nnslr llm-provider use strata
  ```

  `nnslr llm-provider list` lists the providers (never the keys); then `models ID`, `remove ID`, `use none`. Without `--model` it takes the first model the server lists.
- **Where the key is**: in `data/web/private/llm-providers.json` (permissions 600, folder 700, outside git). `NNSLR_LLM_PROVIDERS=/full/path.json` moves the file. The key never leaves the server: no page, answer, log or report contains it, and the browser only knows that there is one. Leaving the key field empty keeps the saved key; **Remove key** removes it.
- **On the review page**: **Ask AI** (key **I**, in the bar under the photo, next to **Car networks**) shows the AI's suggestion for the frame in a card under the bar, with Keep, Correct, Add, Delete or Not judged for every box. It saves nothing: **Apply** turns it into changes to check, and your **Confirm** saves them as your review, as always; **Dismiss** throws it away. At most two requests to the AI run at a time. **Fit with AI** (**Shift+C**) fits the selected box, or every box of the frame when none is selected, with the same AI; **Fit box** does it without AI, **C** for every box of the frame but those placed by hand (see [Fitting a box](#fitting-a-box-c-and-c)).
- **A whole route**: in the list of routes, **Review with AI** on the routes not finished (until an AI reviewer is chosen in Settings, there is a single **Set up AI review** link in its place, and the same link in place of **Ask AI** on the review page). **Try without saving** tries 20 frames without saving: the suggestions go to `data/ai_reviews/<route>/`, and the review page of the route shows them in the **AI reviewer** card under the photo of every frame tried (with **Apply** and **Dismiss**, like **Ask AI**) and in the **AI trial** filter. **Review and save** saves the AI's reviews, only with a provider that passed the Test. They still have to be confirmed (on the **AI · to confirm** page, in the list «N by AI to confirm»), and they go into training only after a person confirms them: the import leaves them out, and removes the ones imported before this rule. It starts as a job of the panel (`helpers/ai_review.sh`, followed in the Overview), never together with a preparation or an update. Frames confirmed by a person are never touched.
- **The reviews saved by the AI are final**: nobody approves them again, and the next import (`helpers/3_train.sh`, **Import reviews**) puts them into training as AI reviews: `reviewer` `ai/<provider>/<model>`, type `ai`, channel `web`, `label_basis` `ai_review`. Saving does not import and does not train.
- **Measuring a provider**: Evaluate → **AI reviewers**, **Measure** (`helpers/measure_ai_reviewer.sh`): up to 60 frames reviewed by people, always the same ones for every provider. It measures the speed signs found and read right, the agreement on the frames without signs, the false boxes, and the seconds per frame. It saves nothing; the result goes to `data/evaluations/ai_reviewers/`.
- **Who can**: only a browser that has signed in, or the site on 127.0.0.1, changes the providers and uses the AI. The token (API, MCP, agents) can only read the settings, the state of the AI and the measures ([API_MCP.md](API_MCP.md), section 8).

## 5. Common problems

| Message | What to do |
| --- | --- |
| `splitting the dataset needs at least 3 independent reviewed routes (or places)` | Prepare and review more routes, then run `helpers/3_train.sh` again. |
| `the GPU 0 is busy` / the button says "the GPU is busy with another process" | Another training is running (often `openpilot.distill`): wait for it to finish. From the terminal, `--force` starts anyway, and both get slower. |
| `port 8765 is already in use` | A site is already on (the service, or another `nnslr review`): `helpers/2_review.sh` prints the link again, `helpers/2_review.sh --stop` stops the one started by hand. |
| `Sign-in required: reload the page and sign in` | The session ended (7 days without use, signed out, password changed): reload and sign in with name and password (section 3). |
| API or MCP: `401 unauthorized`, `501 mcp_unavailable`, `409 ...` | See [API_MCP.md](API_MCP.md), section 7. |
| `Sign in on the site to use the AI reviewer.` (403 `session_required`) | The AI reviewer works only from a browser that has signed in, or from the site on 127.0.0.1: the token can only read. |
| `Choose an AI reviewer in Settings.` (409 `no_ai_reviewer`) | Account → Settings → AI reviewer: add a provider, press **Test** and choose it in **Who reviews**; or `nnslr llm-provider test ID` and `nnslr llm-provider use ID`. |
| `... did not pass its last Test ...` / `Test ... in Settings first ...` (409 `ai_not_tested`) | The provider did not pass the Test (or was never tested): fix it and press **Test** in Settings (`nnslr llm-provider test ID`). Only then can it review. |
| 429 `ai_busy` | Two requests to the AI are already running: try again shortly. |
| 502 `ai_unreachable`, `ai_http_error`, 504 `ai_timeout` | The provider's server does not answer, refuses (a wrong key, a model that does not exist: the message says `HTTP <code>`) or does not answer within 2 minutes: check it with **Test**. |
| Test: `... takes text only: it cannot see the frames.` | The model cannot see images: choose a vision model (with llama.cpp, its `--mmproj` file is needed too). |
| `there are no stable weights on ... yet` | `--continue` needs a model already published as stable: train from scratch first. |
| A route stays at "videos to link" (`helpers/status.sh`) | `link-videos` found a conflict: see `data/logs/prepare/link-videos.json`. Segments with only the log and no `fcamera.hevc` (left by a fetch before 30 Oct 2026, or by Distill's) are not an error: they are not linked, and they are listed in `log_only`. |
| Extraction or pre-annotation failed | The reason is in `data/logs/prepare/<route>.log`. |
