# Quick guide: from videos to model

How to use `sunnypilot.speedlimits` every day on the server (the LXC with the two V100s), with the three helpers and the web panel. To install the environment from scratch, see [INSTALL.md](INSTALL.md). For the `nnslr` commands one by one, see [upstream-training-guide.md](upstream-training-guide.md).

`nnslr` (Neural Network Speed Limit Recognition) is the name of the project and of its CLI (`.venv/bin/nnslr`): it recognizes speed limit signs with a neural network. The name comes from the project it was recovered from, `openpilot-nnslr-tools`.

Run every command from the repository folder, on the server:

```sh
cd ~/sunnypilot.speedlimits
```

Every operation below is a script of the repository: there are no manual steps to remember. If something is done often and is not a script yet, add it as a helper and document it here.

International sign units (runtime integrated locally on `speed-limits`, no deployment):
[plan](2026-11-02-speed-vision-units-plan.md) and
[verification report](2026-11-02-speed-vision-units-report.md).
`scripts/replay_speed_vision_country.py --help` describes the read-only local GPS
replay. It requires explicit border and experimental policy files; it downloads
nothing, runs no network inference, changes no review/dataset, and contacts no car.

## 1. The full loop

| Step | Command | What you do |
| --- | --- | --- |
| 0 | `helpers/fetch_comma_segments.sh` (on the site: the **comma** pill at the top right, with a green dot when the comma can be reached and accepts the server's key, then **Download new drives**; while it runs the pill shows its percent and bar, the drive it is at ("drive 44 of 46") and the segments downloaded; while a preparation or a code update runs it stays off and says what it waits for, since the two never run together. The comma's address is changed there too: it is saved in `data/web/comma.json` and passed as `--host`. For a new comma the panel walks you through the steps: SSH on and a GitHub user on the comma, the server's public key added to that GitHub user with **Copy**, the address, **Test now**; see docs/INSTALL.md, "The comma, from zero". A comma the server has already logged into once (the time of the last login is in `data/web/comma-seen.json`) and that is now only switched off shows "Last connected …" instead of the steps) | It downloads every drive still on the comma, also the old ones not in dashcam mode, into the folder shared with `openpilot.distill` (`/root/comma-videos`). Every segment of a drive comes in full, the first two, the last two and those with the reverse gear too, so the whole drive is in Sign review and in the training; only drives shorter than 300 s are left out. Distill does not use them: it trains only on the drives it downloads itself (dashcam). |
| 1 | `helpers/1_prepare.sh` | Nothing: it links the videos, extracts the frames (1 per second, plus the exact frame of every sign the comma read) and proposes the signs for every new route. |
| 2 | `helpers/2_review.sh` | Open the link it prints, then confirm or correct the signs. It is the only manual step. |
| 3 | `helpers/3_train.sh` | Nothing: it imports the reviews, checks the dataset, freezes the split, creates `.venv-gpu` the first time and trains. |
| 4 | `scripts/publish_model.sh data/runs/<run>/bundle --no-upload` | Check the bundle. Then, without `--no-upload`, it publishes it on Hugging Face. |

At any time, `helpers/status.sh` shows every route (segments, frames, reviewed frames, objects in the dataset), what is running, the first GPU (GPU 0: its use and memory, with the compute processes of both cards counted) and the disk, and the **next command** to run. It changes nothing.

You can run the helpers again whenever you like: work already done is skipped. `--help` on each one explains its options.

### Useful options

- `helpers/1_prepare.sh --jobs=4`: prepares 4 routes at a time (more cores, faster).
- `helpers/1_prepare.sh --background` and `helpers/3_train.sh --background`: they keep going even if you close the ssh session. The log is in `data/logs/`.
- `helpers/3_train.sh --dataset-only`: only the import and the dataset check, no GPU.
- `helpers/3_train.sh --continue`: a new training that starts from the "stable" weights published on Hugging Face.
- `helpers/3_train.sh --resume=<run>`: resumes an interrupted training (same folder `data/runs/<run>/`).

### Three rules to know

- **Training needs at least 3 reviewed routes.** `nnslr build-splits` divides the dataset into three independent parts, by whole routes: validation and test take about 15% each, and all the rest is train, so every reviewed route is used. The test takes first the routes with the most frames confirmed by a person (`--test-route <route>` puts a route in the test). With fewer than 3 routes it stops. The imported reviews stay in the dataset: nothing is lost.
- **The dataset follows the latest review of every frame.** A frame already imported and then reviewed again (boxes changed, or the review reclassified as AI) replaces its old rows. A frame already imported and then withdrawn is removed. The removed rows stay archived in `data/annotations/replaced/`. `nnslr import-annotations --from-db --dry-run` shows what would go in, what would be replaced and what would be removed, without writing anything.
- **A route already pre-annotated is never processed again.** A new pre-annotation would leave the reviews on the old report, and the import would skip them. Segments of that route that arrive later stay out; `helpers/status.sh` points them out.

## 2. The web panel

The site is in English and looks like `distill-web` and `perception-web` (dark; the **Account** icon at the top right opens the menu with the Dark / Light / Automatic look, the password and signing out). There are four sections in the top bar (on the phone, in a bar at the bottom, like an app): **Overview**; **Data**, with the pages **Drives** (`/prepare`), **Speed review** (`/speed-review`, the one review page: the signs are reviewed on its **Signs** side), **Sign distance** (`/sign-distance`) and **Training dataset** (`/dataset`); **Training** (`/train`); **Models**, with **Versions** (`/models`), **Drive** (`/drive`), **Results** (`/evaluate`) and **Publish** (`/publish`). The pages of a section are under its title. It is one single page that switches tabs without reloading:

- **Overview** (`/`, the start page): at the top, the jobs running, one line each (percent, step, time left) with **Stop** beside it (a tap on the line opens the log), or the last job if it failed; then the loop of the work, four numbered cards in their order: **Drives** (the drives to prepare and who finds the signs, with **Prepare new drives**; with none, **Download** from the comma), **Sign review** (the frames left, in how many drives, the percent confirmed, with **Resume review**), **Train** (as Data › Training dataset says it: the Sign review frames not in the dataset yet, on how many drives, and the last import, with **Import sign reviews**; under it **Training pipeline**, which opens Training › Pipeline and stays while the import runs, [#43](https://github.com/cristianku/sunnypilot.speedlimits/issues/43); until 3 drives are reviewed, how many are) and **Car** (the networks in use that the comma's software does not have yet, with **Publish**, or **Finish publishing** while the build of psa-torque-sunny-testing is owed). Each title leads to its page; the first card with work waiting has a ring and the blue button; a job running for a card takes the place of its button (its **Stop** is in the list at the top); a card whose work is done has a tick. The cards are worked out from the data (drives, review, dataset, `models/active.json` and `models/on-car.json`), not from the sentence of `route_status`. At the bottom, the last three finished jobs (**Show all** for the others). The machine (GPU, CPU, RAM, disk), the processes on the GPU and **Update the site** are in the panel of the server pill at the top: the pill gives the use of each card (*GPU 3·87%*), the panel one row a card (*GPU 0 · 81:00.0*, *GPU 1 · C1:00.0*) with its use, memory, temperature and what holds it. The list of routes `/routes` (Data › Sign review) opens on a summary: the frames confirmed, by you and by the AI assistants, the AI's frames still to confirm, and one tile per group (In progress, To start, Done). A tile shows its list: one list at a time and always one, remembered in the browser, otherwise the first group that has drives.
- **Data** (`/prepare`, formerly "Prepare"): **Download from the comma** and **Prepare new drives**, their progress, and the table of the routes. **Find the signs → Found by** chooses who proposes the signs (Vietnamese YOLO, Our networks, Qwen3-VL) and shows its measure from Evaluate › Proposers (speed signs found and read right, seconds per frame). The choice stays on the server for every browser (`data/web/proposer.json`); until someone chooses, it is the proposer with the best measure. Every preparation takes it, also one started from the Overview's Drives card or with **Try again**, and `helpers/1_prepare.sh` from a terminal without `NNSLR_PROPOSER` (the Vietnamese YOLO only before any choice). With Our networks chosen, the line under it names the cutter, classifier and applicability network in use (**In use now: cutter SignNet, 30 Oct 10:46 · …**, changed in Models); the Overview's Drives card says it too (**Found by Our networks: …**, with **Change**). While a preparation of the site is running, it shows that preparation's proposer and cannot be changed; its card says it too, with Our networks' cutter, classifier and applicability network (those in use when it started). With a SignNet in use, Our networks see only the band at the top of the frame, as the car does: a sign lower down (a road marking, a low sign close by) is not proposed. With Qwen3-VL not installed, or with less than about 18 GB free on the GPU with the most free memory (the card a preparation takes), **Prepare new drives** and **Propose again** stay off, with the reason. Without new routes the page points to the comma's **Download new drives** in the top bar.
  **Read the map**, the card above the routes, is for comparing with the map as it is today: it gives every frame of the prepared drives the map's limit and its road type (town, 30 zone, rural, expressway, motorway, ramp, merge lane, parking, garage), shown as **Map now** in the drive player's card and in its **Server today** lane, never mixed with what the comma knew while driving. Nothing learns from it, and the brain never reads the map. It reads them from the OpenStreetMap map of the server and from the comma's GPS (on the road camera's pictures, the more precise position of openpilot.distill's localizer where it went through the segment and agrees with the GPS). The only network use is the map of a new place (from Geofabrik) and the GNSS orbits of a new day for the localizer. The **Read the map** button runs `helpers/road_types.sh`: the localizer on the segments it has not been through yet (about 20 s of a core for each minute of drive, 6 side by side: some 20 minutes the first time, then a minute or two for each new drive; skipped without openpilot.distill's `.venv`), the GPS of the drives that do not have it yet, were localized since, or have frames it lacks (taken out again after it was read), the maps the drives need (the Geofabrik extracts that hold a drive's positions and are missing on the server, such as a US state or Alsace for a drive near Basel, downloaded at most 5 GB at a time; a download that fails leaves the maps there and the search goes on), the car's speed from their logs (about a minute for each new drive), the map roads near the drives (about 4 minutes, only when there is a new drive or a new map) and the names of the places that name the drives (only with a new map), and the map's limit and road type of every frame in `data/derived/road_types/` (a frame without a position is "no gps": no type from the map, but Speed review still lets a person set it). It starts on click, without a question, and nothing needs to be reviewed first; it says how many prepared drives are not read on the map yet. Once a search has looked for the maps, **Maps** under the button lists the extracts of the server ("Switzerland, Baden-Württemberg, Illinois, Indiana, Missouri"). When drives went outside them, the card says **Maps to download** and a line says what the next search downloads: "4 drives outside the maps: Read the map downloads Alsace and Michigan (≈ 448 MB)". It also says when the last download failed, and why, and names a map bigger than a search downloads (5 GB). Positions on no map to download (the sea, a lake, a GPS fix that jumped) are said too: they stay without a road type. In the US a limit in mph decides the type: 45 mph or less is a town (the arterials of a US town, with shops and signals, also a trunk road at 45 mph), 50 mph and more is rural, never a 30 zone; 35, 40 and 45 mph are always to check. The types are ten: Town, Zone 30, Rural, Expressway, Motorway, Ramp (cyan), Merge lane (cyan over blue), Parking (purple), Garage (magenta) and Unknown (gray). **Ramp** is the ramp of a motorway or an expressway (`motorway_link`, `trunk_link` on the map): the limit signed on a ramp holds only until the carriageway; the map's ramps are always to check. **Merge lane** is the acceleration lane at the end of an entry ramp (the last 50 m of the ramp and the first 200 m of the carriageway): there the car already gives the carriageway's limit, so the driver can speed up to join the traffic. **Parking** is a car park in the open (a car park or one of its aisles on the map) and **Garage** one underground or indoors (`parking=underground` or `multi-storey` on the map, or a stretch without GPS where the car's own speed stays low, at the start or the end of the drive or beside a garage: always to check). There is no general legal limit there, but the car gives 20 km/h in a car park and 10 in a garage (a sign read there counts only if it is lower), because the map often has no limit in car parks and the car could speed up. The page **Roads** (`/roads`), where a person confirmed or corrected the road types and the junctions drive by drive, went on 7 Nov 2026: its address opens Speed review, and what was confirmed there stays in `data/annotations/road_types/` and `data/annotations/junctions/` (the scene network that learnt from them went the same day). The signs and their reviews do not change.
- **Results** (`/evaluate`): the numbers of every version, per network (Proposers, Chain, Cutter, Classifier, Applicability, AI reviewers): two versions are compared only when they were measured the same way on the same test. Its **Drive** view left on 10 Nov 2026: a drive is replayed on Models › Drive, below.
- **Models** (`/models`): at the top, the networks in use (cutter, classifier, applicability, brain) with their numbers. Below, the versions of one of them (the switch, or a tap on its card) in a table to compare: only the recent ones (the one in use and the others of its training, the newer ones that can be put in use, the one on the car or tried on the comma, a training running now; with none in use, all those that can be), the others behind **Show N older versions** (nothing is deleted, the files stay) (speed signs, all signs, and for the classifier the chain with the cutter; under each number, how many signs it is measured on). A row opens its card, with **Use this one**. The cutter is SignNet (`nnslr train-signnet`, the network the comma runs: the 896 × 288 band at the top of the frame, stride 8); the one in use gives the boxes of Prepare's Our networks, of the classifier's false boxes and of the chain: the car's best 5 boxes a frame, from score 0.1 (the car keeps those of 0.3 or more); the chain is judged at 0.3, as the car reads it. **Use this one** is there only for a finished SignNet that fits the car (band 896 × 288, stride 8); a SignNet with another band, or an unfinished one, says why it cannot be chosen. The old Detectors (`scripts/run_detector_sizes.sh`, the detector of a whole pipeline) stay among the older versions to compare, and cannot be put in use; one already in `models/active.json` stays in use until a SignNet is chosen. **Speed signs** and **Every sign** count the signs found at threshold 0.1, with all the boxes that pass (a Detector has a couple of hundred per frame, SignNet a few). **In 5 boxes** counts the speed signs among the 5 best boxes of every frame at any score ("–" for old reports that do not keep the boxes of every frame); the car reads fewer, only the boxes of score 0.3 or more: on the test of 26 October the SignNet on the car finds 152 of the 381 signs (40%) and 120 of the 208 speed signs (58%) at 0.3, with 0.22 false boxes a frame, against 209 (55%) and 130 (62%) among its best 5 boxes at any score. **On the car** marks the networks the comma downloads (the SignNet, the classifier and the brain published in `speed-limits-models`). Each card at the top says whether the version in use is that one: **On the car: this one** in green, **On the car: an older one, 28 Oct 11:15** in orange (two versions often have the same name: the time tells them apart), with what puts it there (**Publish**, on the Publish tab); applicability runs only on this server. A trial on the comma shows instead as **On the comma: … as a trial**. `nnslr on-car` records them (section 6) in `data/models/on-car.json`; they do not change the networks in use. The scene network went from Models on 7 Nov 2026: the brain decides, and no release has had it since. **Publish** (`/publish`) puts the networks in use into the comma's software in one go, with one button, **Publish** (`scripts/send_to_car.sh`): the SignNet, the classifier and the brain in use are prepared as ONNX and checked, published in `speed-limits-models`, the sunnypilot `speed-limits` branch moves to them and `psa-torque-sunny-testing` is built again (a few minutes; its five steps show in place of the button). Then, on the comma: Settings, Software, Check for updates, and install. Above the button, each network in use next to the one the comma's software has (**On the car: this one** in green, **an older one** in orange); the button is there only while one differs, or a build is still owed (**Finish publishing**), and only for a finished SignNet that fits the car (a band of 896 × 288, stride 8) and a brain in use that does not take your pedals and the car's speed (since 10 Nov 2026 Publish refuses one and says so; **Try on the comma**, which copies the sign networks alone, and Models › Drive still take it). Below, apart and optional, **Hugging Face**: a package of the cutter, classifier and applicability in use for other people (**Prepare the package**, then **Publish on Hugging Face**); the car does not need it.
- **Road labeler** (the card at the bottom of Models, `/models`): an offline network that labels Speed review, its base layer (the kinds of road, the roadworks and the road type, from the camera at high definition, the map, the GPS and the speed); what it writes is final, the brain learns it with nothing to confirm, and you correct only where it is wrong; it never runs on the car ([ROAD_LABELER.md](ROAD_LABELER.md)). **Dry run** tries the training on the CPU (a couple of steps of two drives, nothing learned) and **Train** trains it on the GPU from the corrections of Speed review (`helpers/road_labeler.sh train`); both ask first. Its progress shows in place of the buttons: the check of the GPU, the drives read one by one (the first time it decodes their videos), then the epochs with their curve. Each run below says, on validation, how often its road type is right beside the map's, and for each kind of road and the roadworks its precision and recall and whether it writes into Speed review or why it is held back. Each run also says the road types it writes, what its last Prepare wrote head by head (marks written, older ones taken out, the ones you kept, seconds of road type), and **in Speed review** on the run prepared last, the one Speed review shows. **Prepare Speed review** on a run (`helpers/road_labeler.sh predict --all`) writes, for every drive, everything its heads earned through the gate (reviewer `net/<run>`): the marks of the kinds of road and of the roadworks, and its layer of road types over the map (`derived/road_labeler_types/`); a head held back writes nothing. It replaces what an older run wrote, its marks that you did not keep (one you went past with checked to here is kept) and its layer, in one write a drive kept in the history; your marks, removals and checks and the map's tunnels are never touched. **Chances only** writes nothing into Speed review (the chances in `derived/road_labeler/`). A real run takes a free GPU of its own and is refused while none is free, by the server and again by the helper on its card (one line, exit code 3: another compute process on it, or more than 10% of its memory taken); a **Dry run** is not, it runs on the CPU and takes no card.
- **Drive** (`/drive`, Models › Drive): to see, before a set of networks goes on the car, what the comma's screen would show with it along a drive you recorded, and to keep the drives where all of it was right as the test of the next sets. The server replays the drive through the car's own vision loop (the code of the sunnypilot clone, `openpilot/sunnypilot/speed_limits`): every frame of the road camera's video and the car's own signals from the logs, in the order `speedvisiond` got them. The map is never read. It took the place of the Drive view of Results and of the Regression tab on 10 Nov 2026; `/regression` opens it.
  **Networks** chooses the set: **On the car** (the release in the sunnypilot clone, what the comma downloads) or **In use** (the versions in use on Models, exported first as Publish would export them, and again when one of them changes). Under it, each network of the set (SignNet, Classifier, Applicability, Brain) with its version. The list has every drive, newest first, with what it has for that set: **Certified**, **Replayed**, and for a certified drive replayed with it **identical** or for how many seconds it differs.
  A tap opens the drive (`/drive?drive=<route>`, **‹ Drive** to go back): the drive player, and on its picture the comma's screen as the car draws it. (The player's video is the comma's road camera, 20 frames a second: the server makes its MP4 once, as soon as a drive's minutes have arrived or the first time a player shows it, on the GPU, about a minute for a 45-minute drive, or on the CPU when the GPU's memory is taken; `nnslr drive-video` makes it by hand.) The fuchsia square is the speed to hold. Under it the reading square: the confidence, the last limit read and the metres to it, with a red border while the sign is in view and a pulse when it is read. A road sign read (TOWN, MWY, EXP, crossed out at its end) never takes the limit's place: it goes in a small box under the square, red while in view, until the next sign is read (as on the comma since 11 Nov 2026, `sign_reading.square_and_road`). **Boxes** adds SignNet's boxes of the frame read, each with the classifier's reading and confidence and, for the signs the applicability network judges (limits, their end, zones), whose road it gave it to: *OURS*, *other road* or *road unsure* (red a sign of our road, grey and dashed one of another road). **Full screen** (the last button of the video's bar, always in view; F on a computer) shows the picture alone, with the comma's screen, the boxes and the car's speed on it, over the whole screen; a phone turned on its side does it by itself, and upright again the page comes back (an iPad keeps the page). Where the browser has a full screen for a page (Android, an iPad, a computer) it uses it, and the button also turns an Android phone to landscape; iPhone Safari has none, so there the picture fills the window. In full screen the commands show while the video is paused and hide while it plays, a tap on the picture plays or pauses, and the same button goes back to the page ([#49](https://github.com/cristianku/sunnypilot.speedlimits/issues/49)). **Source** chooses what is drawn: **Comma that day** (what the comma logged on that drive), **On the car**, **In use**, and on a certified drive **Certified**. The lane **Hold** is the speed to hold, **Signs** every reading. On a replay whose brain learnt the road type, the lane **Road type · brain** is the road type the brain names at each of its steps, in Speed review's colours, and **Road type (brain)** beside the player says it with its probability (*Motorway · 93%*): its training head `type_head`, applied to the memory the car's own brain makes in the replay, so it is what that brain thinks of the road; the car does not show it ([#48](https://github.com/cristianku/sunnypilot.speedlimits/issues/48)). **Compute** replays the drive with the set shown (`helpers/simulate_drive.sh`); it is there while the drive has no replay with it, or one made with other networks, another code of the car or other car settings than today's, or without the road type of a brain that has it (a replay made before 10 Nov 2026). Such a replay is out of date, and says so in orange: on the drive, a box above the squares lists what changed since it was made (*Brain 2026-11-10_0111-brain-s1 → 2026-11-10_2051-brain-s2*, *Car code changed*, *Car settings changed*); in the list, a badge names them (*Out of date: SignNet, Brain*), the versions in its tooltip ([#54](https://github.com/cristianku/sunnypilot.speedlimits/issues/54)). Every replay keeps what it was made with in `<set>.json.gz.meta.json` (each network's id and SHA-256, the car's code, its settings, the brain's road type head), and `simulation.changes` compares it with the set of today.
  **Certify this drive**, when all of it is right, keeps that replay as the drive's reference, with who and when (**Remove** takes it back; the replays stay). It keeps the replay on the screen: when the drive was replayed again in the meantime it says so and certifies nothing. The certified replay keeps, for every frame read, both squares, SignNet's boxes, the car's signals and the brain's input row, the minute and frame of the video, the SHA-256 of each minute's video and log, and every network's id and SHA-256. From then on a replay of that drive is compared with it frame by frame, the regression test: **Replay the certified drives**, on the list, replays them all with the set chosen, one after the other. A drive then says *Identical to the certified drive.*, or for how long the speed to hold differs and on how many frames the reading (while a sign is in view: the sign, the other-road mark and the pulse; not the confidence and the metres, which move by a point or a metre with any other network, nor the grey last sign after it). A replay that read another video or log of a minute than the certified one is never identical. The lane **Differs** shows where (red the speed to hold, orange the reading; a tap goes there), **Previous** and **Next difference** step through them, and for the frames with another speed it says whether the brain was given the same inputs since its memory last started again in both (the brain changed) or other ones (what is read before it changed, another video or another car code for the picture; always so when the brain is the same). Two brains that take other input groups (one of before 10 Nov 2026 with the car's speed and the pedals, one without) are compared on the groups both take. A replay made before 10 Nov 2026 is not shown any more: **Compute** makes it again.
  A replay always runs on a V100: the card decodes the video and runs the networks. It takes about 1 GB of a card and shares the one with the most free memory with what runs there (a training, or strata holding both cards), and one replay runs at a time. When no card has about 2 GB free the buttons are off and say how much is left, and the helper stops with one line (exit code 3): a replay never moves to the CPU. It is not the car bit for bit: the video comes after the comma's encoder and the networks run under onnxruntime, not tinygrad, so a confidence right at a threshold can fall on the other side. The page draws a replay on the clock of the drive's logs: a drive whose logs are not read yet (**Read the logs**, Speed review) says so. The replays stay in `data/derived/simulation/<route>/<set>.json.gz`, the certified ones whole in `data/simulation/certified/<route>.json.gz`, listed in `data/simulation/certified.json`.
  The curves of the driving models that the Regression tab drew (`scripts/run_regression.sh`, `data/regression/`) have no page for now: they come back as switches of this one.
- **Publish** (Publish tab) and **Try on the comma now** (on the card of a SignNet, Models › Versions, Cutter): Publish takes the SignNet in use, Try on the comma now that SignNet; both take the classifier in use, and ask first; both refuse, before starting, a SignNet that does not fit the car (a band other than 896 × 288 or a stride other than 8) or has not finished; Publish also takes the brain in use, and drops the published one when none is in use (the scene network of older releases always), while Try on the comma now keeps the build's. **Publish** (`scripts/send_to_car.sh`) publishes them in `speed-limits-models`, moves the sunnypilot `speed-limits` branch to them and builds `psa-torque-sunny-testing` again (a few minutes; nothing is published or built when they are already there); then, on the comma: Settings, Software, Check for updates, and install. **Try on the comma now** (`scripts/try_on_comma.sh`) copies them straight onto the comma over ssh, without publishing or building: they last until the comma's next software update. Before copying it checks the comma (it answers, it is parked, its build has speedvisiond, Show Vision Speed Limit is on or Speed Limit Source is Map Data + Vision or Vision Only) and the networks with the comma's own code (their contracts against its `vision.py`, then its `read_signs` on 5 reviewed frames, the confirmed speed read on 3 at least); then it waits up to 6 minutes for the parked comma to compile them, and puts the build's networks back itself when it does not. While a trial is on, the Models tab marks the SignNet **Trying on the comma** and shows **Back to the build's networks**. Its button is off, with the reason, when the comma does not answer on the network (checked at most once a minute). Its job shows at the top of the Models page while it runs, Publish's on the Publish tab. With nothing to publish the button reads **Build again**: the networks stay, `psa-torque-sunny-testing` is built once more (`--rebuild`), for code changed on `speed-limits`. The card shows only jobs of this button: a failed one finished from a terminal reads "failed, finished later".

The numbers: the main one is **late_s**, vision's zero minus yours in seconds: *Vision's zero comes 0.51 s after yours* (+, late) or *before yours* (−, early); the summary shows the median over every sign marked, with the smallest and the largest. **In metres** (late_m) comes second: vision's last distance plus the metres driven between the two zeros, and it includes speedvisiond's processing delay times the speed (its message is sent after the frame; the builds of 3 Nov 2026 take it off with the lead), so it is not the error of the distance alone. A mark on a minute whose video and logs are not in sync to the frame is kept but left out of the medians. Only a person on the site marks: signed in, or the person at the server itself on a site served only on 127.0.0.1 without sign-in (the reviewer is then `local`); no agent, no MCP tool, no REST write, no CLI, nothing automatic; on a read-only server the buttons are not there and the marks are only shown. Every mark is a line added to `data/annotations/sign_distance/<route>.jsonl` (the sign, the mark, the minute and frame, the frame's time from the server's encode index, who and when); the file is never rewritten, and Undo is a line too. A mark whose sign is no longer found after the logs are read again is matched again by the time of its sign, else by its frame's time (the window whose zero is nearest; a tie matches none), else kept and counted apart, never dropped. The reading of the logs keeps vision's distance exactly as the car logged it (never rounded); a drive read before that says *The logs of this drive are to be read again* until Read the logs reads it again. The countdown itself is speedvisiond's (`vision.py` in sunnypilot): a change to it is a change of `vision.py`, then measured again here. **What the car did here ›** opens the drive in Speed review.

By the names of the code, the blocks say what it gets on the car (the picture, its memory `h` and the groups of `INPUT_SIZES` a training of today gives it, with `pedals`, `speed` and `engaged` never; since 9 Nov 2026 `motion` too: the turn signals, the steering wheel and the yaw, `carState` and `deviceMotion`, given at every step on the car as in the training, so a brain trained since then needs a car build with it), what it says there (`speed`, `next`, `metres`), the answers only its training has (`speed`, `next` and `metres`, `works_head`, `road_head`, `type_head`) and the seconds that answer nothing (`no_speed`, `stopped`, `cruise`, `left_out`, `boundary`, `no_frame`, `no_road_type`); `tests/review/test_brain_card.py` keeps that list equal to the code. First it reads the signs of those drives as the car does today, with the brain's pictures (`nnslr road-type-signs --labelled`): a training is refused on a drive not read so, and since every drive the brain learns from is read, the first reading takes a while; a drive already read by today's reader is not read again. A drive already read by those networks is not read again; a new network in use reads them all again. Nothing in Sign review changes, and these signs are never an input: the brain is given what the car reads. Then it trains three seeds, one after the other on one GPU (both cards come with part C of [#29](https://github.com/cristianku/sunnypilot.speedlimits/issues/29)), or seed 0 alone with **Seeds** › **One** (about a third of the time; `NNSLR_BRAIN_SEEDS=0`), with their curves on one chart: how far the speed is from the answers on validation, the frames it says right (within 2 km/h), the road type `type_head` names right on validation (**Road type right on validation**, since 10 Nov 2026; on each type in **Values per epoch** and in the epoch line, `val_types` and `val_type_<type>`), the train loss. Validation never changes the training: each seed keeps its last epoch, and the road type is only measured there. Before the click the page says how many dashcam drives it learns and their hours (*12 drives, 9.4 h*; the log of a training and of its dry run starts with the same numbers). The drives of a run are those its dry run takes when it starts: kept in `runs/<name>/routes.json`, they go with `--route` to every step and every seed, so a drive read during the run waits for the next one (and the seeds stay alike); while there is no dashcam drive, **Train the brain** is refused with *No drive to learn from: sunnypilot was on in every drive with its logs read (N); drive with sunnylink › Toggles › Enable sunnypilot off*. It says too on how many drives with their logs read it learns, how many seconds of answers go to learn, to watch and to test, on how many of the seconds to learn from the signs answer the next limit, how many drives it reads first as the car does and how many our networks read first, and for each kind of road marked in Speed review the seconds to learn from on it and checked off it. With **Road types** on it says too how many seconds with your speed have no road type and stay out, and how many drives have none at all. The next limit is learnt on every drive our networks read (his rule of 8 Nov 2026): within 100 m of a sign of our road, and *no limit ahead* only where every frame of the 130 m ahead was read; a sign whose road the applicability network could not tell on any of its pictures masks its approach, and a sign nobody could read within 3 s of a number is that number seen from far. Where you confirmed a frame in Sign review its signs are yours, and a sign you boxed replaces theirs of the same kind within 3 s, whatever road you gave it: on our road their pictures of it make it longer, with your reading. A reading by networks no longer in use is not used; without Our networks whole in Models the next limit comes from your Sign review alone, and the page says so. Their mistakes are answers too, fewer as the networks get better; a drive they never read keeps only what you confirmed. **Signs: Cutter**, **Signs: Classifier** and **Signs: Applicability**, under the brain's choices, name the three networks that read the signs the brain learns from, the same three for what it gets and for its next limit (the ones in use first): the applicability network leaves out the signs of another road (an exit, a side road) as speedvisiond does on the car, so a 60 at the side of the motorway never reaches the brain. Without an applicability network the brain does not start. The run keeps the choice (`networks.json`, read once at its start; a run started again keeps it) and Models shows it under the brain as *Signs read by*; a drive not read by these three is read again when the brain starts ([#31](https://github.com/cristianku/sunnypilot.speedlimits/issues/31)). **Roadworks**, **Road conditions** (On by default: the brain also learns to tell each road condition of Speed review (narrow, country, gravel, potholes…), aside, as the roadworks; Off leaves them out, and its run shows the chip *no kinds of road*), **Road type (map)** (On by default since 8 Nov 2026: only the seconds with a road type go into the training, the map's type of **Read the map** (Data › Prepare) with your corrections over it, and the brain also learns the type aside, never as an input; Off learns every second with your speed, and its run shows the chip *no road types*), and **Picture** (grid by default, or mean) are its choices. The gas, the brake and the car's speed are never inputs since 10 Nov 2026: your speed is the answer, and the brain trained with them followed it on the road (**Driver's inputs** is gone; a run of before that had them still shows the chip *driver’s inputs*). A training started from the terminal shows up with its steps and charts (from its `data/logs/train-<run>.log`), but it is stopped from the terminal. An action that is off has the reason under it.

The **Stop** window says what is left for each action: the download and the install of Qwen3-VL resume from where they were, the training of the pipeline has **Resume**, and a measure and **Propose again** start over. When the log shows a known fault (GPU out of memory, disk full, comma not answering, ...), a failed job says in one sentence what went wrong. It has **Try again** if it is a download, a preparation, the install of Qwen3-VL, an import or the measure of a proposer. The exit code and the paths stay in **Details**, which also says how long the job took and has **Stop** while the job runs. The measure of a proposer is named after it ("Measure Qwen3-VL") and counts the frames done. **Propose again** has a single time left, the server's. The list of recent jobs shows the last 12. **Update the code** runs `helpers/update.sh --no-link` (section 3), that is `git pull` and a restart of the site; it starts only when no preparation, training or AI review is running.

**Download from the comma** runs `helpers/fetch_comma_segments.sh` with no arguments (step 0): every drive still on the comma, over ssh with this machine's key (`Host comma` in `~/.ssh/config`), with no need for `ssh -A`. To read the comma's logs (the length of the drive) it uses `COMMA_FETCH_PYTHON` when it is set, otherwise the Python of `../openpilot.distill/.venv`, which has openpilot's `LogReader`. Without either of them, the button stays off with the reason. It does not start together with a preparation: both write the links in `data/raw/routes`. After the download, the next step is **Prepare new drives**.

The panel runs only its own fixed actions, never just any command, and only one of each kind at a time (download, preparation, AI review); the trainings and the other GPU work of Train and Models run two at once, one per GPU (the two GPUs, below). It counts the ones started from the terminal too, including the download of `openpilot.distill`. It is protected like the rest of the site: a token on the LAN, and the buttons accept only requests from the page itself. The logs of the actions are in `data/logs/panel/`; the last line of each one is the exit code.

The server has **two GPUs**, Tesla V100s of 32 GB numbered as nvidia-smi numbers them: **GPU 0** on bus 81:00.0 and **GPU 1** on C1:00.0 ([#29](https://github.com/cristianku/sunnypilot.speedlimits/issues/29)). A training, the regression, the road labeler, the measure of a proposer and the install of Qwen3-VL each take the free card of lowest index for themselves, and start only while one is free; the job gets `NNSLR_GPU_INDEX` and `CUDA_VISIBLE_DEVICES` with `CUDA_DEVICE_ORDER=PCI_BUS_ID`, so CUDA counts the cards as nvidia-smi does. Two of them run at once, one per card, with these exceptions: **Import sign reviews**, the detector and reader (**Train a model**, from any starting point, and its **Resume**) and **Install Qwen3-VL** run beside no other of these; the brain, the regression, the replay of a drive, the road labeler's training, **Prepare Speed review**, the signs on every frame and the measure of a proposer each run once at a time, never two of the same; and never together the brain and the regression, nor **Prepare Speed review** beside the brain, the regression or the road labeler's training. Any other pair runs, each on its own card (a cutter and a classifier, a cutter and the brain, two cutters…), as the tooltip of the Train buttons says. When no card is free, a cutter, classifier or decider training shares the card with the most room with trainings of those three kinds and replays of a drive ([#41](https://github.com/cristianku/sunnypilot.speedlimits/issues/41)), never with the brain, a preparation or a program the server cannot name: 4 GB are kept for each while it starts (about 1 GB each in use today), and it waits only when no card has them. Such a training gets `NNSLR_NUM_WORKERS`, the cores divided among the trainings that run with it (half each for two, as the scripts' default; 6 of 20 for a third). A button that cannot start says why (*A cutter training is running*; with both cards held *both GPUs are busy: a cutter training on GPU 0, a program the server cannot name on GPU 1*); a step of the pipeline waits instead. The brain trains on one card for now (both with part C of [#29](https://github.com/cristianku/sunnypilot.speedlimits/issues/29)). A preparation (**Prepare new drives**, **Propose again**) takes the card with the most free memory and shares it with what runs there, Qwen3-VL only with about 18 GB free on it, and no training starts on that card while it runs. The replay of a drive (Models › Drive) does the same, with about 2 GB free. Work of these kinds started from a terminal counts as its kind of job; it and the training of `openpilot.distill` hold the cards whose `/dev/nvidia` files they have open (every card until one is found), and a card with compute processes of nobody known is held by *a program the server cannot name*. From a terminal, `NNSLR_GPU_INDEX=1` puts a run on the second card (section 5). The two cards share the CPU: the cutter and the classifier each read their frames with half the cores, so a cutter beside a classifier takes every core and the two do not go twice as fast; the cutter beside the brain is the pair that pays off, as the brain's seeds read their frames with no workers (its reading of the signs, step 3, takes half the cores and then about three quarters for the next limit, and for those minutes also the other card when no compute process and no other job holds it: the panel names that card as the brain's and starts no training there until step 3 gives it back).

`NNSLR_PANEL_ACTIONS=0` (in the environment of the server; for the service, in `/etc/speedlimits-web.env`) makes the panel read-only, for example when other people use the site to review.

## 3. The always-on site: the `speedlimits-web` service

To keep the site and the panel always on, even after a restart of the server, install the systemd service once (as root):

```sh
cd ~/sunnypilot.speedlimits
helpers/2_review.sh --stop                        # if you had started the review by hand (port 8765)
scripts/install_review_service.sh --dry-run       # shows what it would do, changes nothing
scripts/install_review_service.sh                 # installs, starts and prints the link
```

The service listens on `0.0.0.0:8765`. It restarts by itself if it stops, and at every boot. Running the install again does no harm: it rewrites the service only when `deploy/speedlimits-web.service` changed, and it does not touch the token.

On the server, `data/derived` (frames and videos, about 185 GB) is on the LXC's local disk with the review databases. It was on the TrueNAS share for one day, 9 Nov 2026, and the lists were too slow there (docs/INSTALL.md, "data/derived on the local disk").

### Signing in from the browser: name and password

On the LAN the site asks you to sign in with a **name and password** (pages, panel and images). The **first visit** creates the administrator: the page asks for the **setup code**, which is the server's access token, then for the name and the password (at least 12 characters). From then on the token no longer opens the site in the browser: it is only the key of the `/api/v1` API, of MCP and of the agents that send it in the `X-Review-Token` header.

- The **Account** page (at the top) shows who is signed in, signs you out (also from every browser) and changes the password. After the change, the other browsers have to sign in again.
- A session lasts 7 days without use, 30 days in all. 5 wrong attempts from one address block it for 15 minutes.
- The sign-in files are in the data folder, under `web/auth/` (`admin.json`, `sessions.json`, permissions 600; the password is saved only as a scrypt hash).
- **Forgotten password**: on the server, in the folder of the clone, run `helpers/reset_password.sh`. It stops the site, moves `web/auth/admin.json` of the data folder to `admin.json.<time>.old` and starts the site again (the service, or the site started by `helpers/2_review.sh`). The next visit asks again for the setup code, then for a new name and password. Reviews and settings stay; every browser has to sign in again. The sign-in page mentions it under **Forgot the password?**.
- Old links with `?token=...` no longer open the site: they lead to the sign-in page.
- Started by hand only on `127.0.0.1` (without `--host 0.0.0.0`), the site stays open to this computer without signing in, as before.

### The public page: smartspeed.14bodhi.com

`https://smartspeed.14bodhi.com/` shows the project to anyone, with no sign-in. ### People from outside: the reviewers

Other people can do review work on the drives you give them, and nothing else: no training, no import from the comma, no panel, no Settings, no API. Nobody from outside is ever an administrator.

**Who they are.** Accounts live in Authentik (`auth.14bodhi.com`, group `reviewers`), created and removed by the cluster's administrator. Two-factor sign-in has to be enforced for that group before anyone comes in: Authentik skips it by default. A request counts as a reviewer only when it arrives from the proxy (`NNSLR_PROXY_IPS`) and carries the proxy's secret (`NNSLR_PROXY_SECRET`, header `X-Speedlimits-Proxy-Secret`); a request with neither is the normal site, a public name (`NNSLR_PUBLIC_HOSTS`) without them is refused. The cookie and the token of the administrator count for nothing on that way in, and `/api/v1` and `/mcp` are closed there.

**What they do.** In **Data › Reviewers** add the user name of the Authentik account, then click the work on each drive: Sign review (the Signs side of Speed review), Sign distance, Speed review (Speed review only on a drive with sunnypilot off, the only ones the brain learns from). The person sees **My reviews**, with the day and length of those drives and a button for each kind of work. The site checks the assignment on every request, so taking the work back counts at once. The list is in `web/auth/assignments.json` of the data folder.

**What they see.** Pictures and video of those drives. The names of the places, the GPS positions and the paths on the server are taken out of every page and answer. The notes of earlier reviews stay, and they can name a town; so does a town sign in the picture: the video always shows where the car was.

**What they save.** It goes in as a person's review signed `guest/<name>`, whatever the page sends, and enters the dataset at the next import like yours; their blocks, roadworks marks and marks of the kinds of road of Speed review reach the brain's next training as yours do (they mark with the kinds there are and add none, and set no road type). On the drives you give them they can change labels already there: Sign review and Speed review keep the history. So give a person only the work you want from them.

**Where they work.** On a machine of their own, the review box (`speedlimits-reviews`, on serverone2), kept apart from this server: it holds only the drives given to someone, with no training, no models and no key towards here. You keep working on `limits.farm.14bodhi.com`. A drive you give in **Data › Reviewers** goes there at the next copy; every 5 minutes, or with **Update now**, what people saved comes back and goes in as if saved here. The card at the top of the tab shows the machine, its drives, the last copy and anything refused.

What goes: the frames, the road and wide videos, the report and the reduced logs. What stays here: the raw logs, the GPS positions, the names of the roads and the map's ids of the roads. A reduced log travels with its track moved around 0, 0, because Speed review reads its turns, and of the positions only the country of each frame goes, so Sign review still proposes it. A saved review takes its position back when it returns. The video can still show where a drive was.

What comes back is read as a stranger's: only the drives and the work given, only under the names of those who hold them. A frame changed on both sides keeps yours; the other is saved in `web/review_box/aside/` of the data folder, and the card counts it.

**Review completed** on their list ends that work: the next copy takes the results and the work back, and when nobody holds work on the drive any more it leaves the machine a few minutes later.

**Turning it on** (once, when the proxy is ready):

```sh
scripts/setup_guest_access.sh --proxy-ips 192.168.200.161 --public-hosts smartspeed.14bodhi.com --dry-run
scripts/setup_guest_access.sh --proxy-ips 192.168.200.161 --public-hosts smartspeed.14bodhi.com
```

It writes the three settings in `/etc/speedlimits-web.env`. The secret is made there and never printed: the cluster's administrator reads it from that file and sets it in the proxy. The service reads the file when it starts, so it needs a restart. `--new-secret` changes the secret, `--off` closes the way in. Until then Data › Reviewers says that the sign-in from outside is not on: you can prepare people and work, nobody can come in.

### The token (setup code and API key)

The place to look for it is the **`.env` file of the repository** (`~/sunnypilot.speedlimits/.env`), the line `NNSLR_REVIEW_TOKEN=...`:

```sh
grep NNSLR_REVIEW_TOKEN ~/sunnypilot.speedlimits/.env
```

- `.env` is in `.gitignore`: it never ends up in git or on GitHub. It has permissions 600 (only root reads it).
- Whichever needs it first creates it: `helpers/2_review.sh` or `scripts/install_review_service.sh`. The install of the service uses the token already in `.env`; if there is none, it creates one and writes it in `.env`.
- The systemd service reads it from its own copy, `/etc/speedlimits-web.env` (permissions 600). Every install writes the same value back into `.env`.
- The install, `helpers/2_review.sh` and `helpers/update.sh` print the address of the site (`http://<server IP>:8765/`), without the token.

Do not share the token: whoever has it can create the administrator while there is none, and can use the API. To change it, write the new value (at least 16 characters, from letters, digits, `-` and `_`) in `/etc/speedlimits-web.env`, then run `scripts/install_review_service.sh` (it copies the value into `.env`) and `systemctl restart speedlimits-web`.

### Updating the code

```sh
cd ~/sunnypilot.speedlimits
helpers/update.sh
```

`helpers/update.sh` runs `git pull --ff-only` (it stops when there are local changes), updates `.venv` when `pyproject.toml` changed, runs `scripts/install_review_service.sh` again (it rewrites the service only when it changed) and restarts the service. Without the service, it restarts the site started by `helpers/2_review.sh`. At the end it prints the link, except with `--no-link`: that is how the **Update the site** button runs it, in the server panel (the GPU/CPU pill at the top right). The button is off, with the reason, while a job runs that the update cannot interrupt. After the confirmation, the site follows the job and reloads the page only when it succeeded; otherwise it writes "Not updated." and why (in the panel and in a notice at the bottom).

The service has `KillMode=process`: a restart stops only the site, not a preparation or a training started from the panel. After the restart the panel finds them again as "running".

### Checking and stopping

```sh
systemctl status speedlimits-web                     # is it on? since when?
journalctl -u speedlimits-web -n 50                  # the last lines of the server (also "Pannello: avviata ...")
systemctl stop speedlimits-web                       # switches it off (it starts again at the next boot)
scripts/install_review_service.sh --uninstall     # removes the service (the token stays)
```

### REST API and MCP (review without a browser)

The same service also offers the **REST API** (`/api/v1/...`) and, with the optional MCP dependencies, the **MCP** server on `/mcp`, to review with `curl`, a script or an AI (Claude Code, Codex) that runs on its own computer. Everything is in [API_MCP.md](API_MCP.md). In short:

- the token goes **in the header** `Authorization: Bearer <NNSLR_REVIEW_TOKEN>`, never in the address; it is needed on 127.0.0.1 too;
- the same rules and the same database as the page; the panel (Prepare, Import, Train, Update) cannot be reached from the API or MCP;
- install the MCP dependencies once and restart the site: `helpers/setup_mcp.sh --restart` (see "Local install for MCP" below);
- MCP also works without HTTP, over ssh: `helpers/mcp.sh` (with `--read-only` for a trial without saving; `NNSLR_MCP_READ_ONLY=1` in the service does the same on `/mcp`);
- the reviews of an AI are saved as `ai/<name>`, type `ai`, and they do not change the confirmations of a person. They are final, like those of a person: `helpers/3_train.sh` imports them into the dataset without another approval, with the AI provenance (`ai/<name>`, `label_basis` `ai_review`, channel). Confirming does not import and does not train: import and training are started separately.

#### Local install for MCP

Some things are not in git, because they are installs or settings of the machine. `helpers/setup_mcp.sh` does all of them. You can run it again whenever you like (it skips what is already there):

```sh
cd ~/sunnypilot.speedlimits
helpers/setup_mcp.sh                         # only the MCP SDK in .venv (extra [mcp])
helpers/setup_mcp.sh --claude                # + Claude Code in this folder, for the review sessions
helpers/setup_mcp.sh --claude --effort=low   # as above, with another effort (default medium)
helpers/setup_mcp.sh --restart               # + a copy of the database if it must be migrated, and a restart of speedlimits-web
```

| What | Where it ends up | Why it is not in git |
| --- | --- | --- |
| MCP SDK (`mcp` 2.x and its dependencies) | `.venv` | installed packages |
| MCP server `nnslr-review` (stdio, `helpers/mcp.sh`) for Claude Code | `~/.claude.json`, for the folder of the repository | Claude Code configuration of the machine |
| `mcp__nnslr-review` tools allowed without asking, `effortLevel` of the sessions | `.claude/settings.local.json`, listed in `.git/info/exclude` | a local setting: the review sessions started here (also the remote ones of the bridge environment) do not stop to ask, and do not use the high effort |
| copy of the database before the migration | `data/annotations/review.sqlite.bak-v1-<time>` | data |

To take the permissions away from the sessions, delete `.claude/settings.local.json`. To remove the MCP server: `claude mcp remove -s local nnslr-review`.

Reviews an AI made from the page (with a name like `Codex` or `ChatGPT`) count as human. `nnslr review-reclassify-ai --reviewer Codex --reviewer ChatGPT --dry-run` counts the ones to change; without `--dry-run` it marks them as AI (a new review in the history, same boxes). Make a copy of the database first.

The review database updates itself to version 2 at the first start of the new code (it adds the reviewer type and the channel; the reviews already made stay "human, from the page"). After that, an old `nnslr` can no longer open it.

### Fitting a box (C and ⇧C)

On the review page a rough box is fitted to the sign under it in two ways:

- **Fit box** (key **C**, and the chip under the sharp crop of the selected box; **Apply previous** does it by itself on the boxes it carries): **C** fits every box of the frame, whichever is selected (after **Apply previous**, after **Apply** of the AI, a box just drawn, a box you moved or resized by hand); the chip fits only its own box. The fit that **Apply previous** runs by itself leaves the boxes you moved or resized by hand since a fit last moved them where you put them, since nobody asked for it; **C** fits them too ([#13](https://github.com/cristianku/sunnypilot.speedlimits/issues/13)). The server's CPU fits them in one request and well under a second, with no AI provider (`nnslr_tools.box_fit`: colour masks and grabCut ranked by a small tree model, edge and MSER candidates ranked by three tiny networks, their mean pulled back toward your box as far as it already agrees with it). On drives left out of the training of its weights it takes a rough box from a mean IoU of about 0.64 with the box a person drew to about 0.78 (the two constants of the mean and the pull-back were chosen once on boxes from the same drives, so the figure is a little optimistic). When it finds no better box (no sign there, or your box already right) or moves no side by a pixel, it says "No better box found: kept as it was" and leaves the box, and the frame, as they are. A fitted box is an unsaved change, saved only by your **Confirm**.
- **Fit with AI** (**Shift+C**, the chip beside it): the AI reviewer of Settings fits the selected box, or every box of the frame when none is selected, one at a time. It is slower and needs a provider that passed its Test; use it when **Fit box** misses.

**Square boxes** ([#66](https://github.com/cristianku/sunnypilot.speedlimits/issues/66)): hold **Shift** while drawing a box or dragging a corner and the box is a square; **Q**, or the **Square** chip before **Fit box**, makes the selected box a square on its centre, its side the mean of its width and height. Boxes of one shape teach **Fit box** better.

Neither moves a box with **Panel below** on **Hours** or **Wet**: it holds the disc and the plate, and both fits look for the disc. The page says "The box takes the disc and the plate: kept as it is."

Both work only for a browser that has signed in, or the site on 127.0.0.1; the token alone cannot fit boxes. At most two fits run at a time. The models are `src/nnslr_tools/box_fit/colour.npz` and `edges.npz`, plus the box refiner `refiner.onnx` when it beat them, a small CNN used only on a box under 30 px a side (one pass, then the two rankers on its box; on routes left out it fits small signs and gantry displays better, and an already tight box slightly worse): `scripts/train_box_fit.sh` trains them again on every box people drew (the candidates cut on the CPU in about 2 minutes, then the trees, the networks and the refiner trained on a V100, never on the CPU: without a card it stops, [#65](https://github.com/cristianku/sunnypilot.speedlimits/issues/65)), and the site uses them after its next restart. In the portal it is **Models › Fit box**, the action "Train Fit box": a dry run, the training with or without the refiner, its progress, and the last summary of each part (the mean IoU on drives left out of the rough box, the rankers and the refiner, and whether `refiner.onnx` was written). The model files are tracked in git: commit them after a run, or Update the site stops on the local changes.

### What the classifier gets

The zoom of the selected box lies inside the photo, in its top corner on the other side from the box (under the comma's limits in Speed review); a click elsewhere on the photo closes it, as it clears the selection. In the zoom's corner, the square **Classifier** shows that box as the network gets it: the crop its training cuts, made by the server with the training's own code (`training.crop_source`, `crop_rectangle` and the 160 × 160 bilinear resize, through `crop_cache.review_crops`), its proportions lost. Its caption has two lines. The first says what it is and the box's size in pixels of the picture it was cut from, for example *Classifier · 74×74 px*. The second names that picture: *from 2688×1520* on a drive recorded at full definition, *from 1344×760* on older drives ([#27](https://github.com/cristianku/sunnypilot.speedlimits/issues/27)). While a corner is dragged, and wherever the server cannot make the crop, the page draws the square from the photo on screen and the second line reads *browser preview*; the server's crop takes its place once the box stops moving. The small grid button at the end of the second line shows four small crops: top left, in a blue frame, the training's crop of the box as drawn; in the other three, the box as the training varies it across epochs (moved and resized; the tilt and the colours are not shown). A second press goes back to the single square. It saves nothing.

### Signs in the US (mph)

On a frame whose country is the US (the one picked, else the one its GPS gives), Sign review shows the signs as they are there: the white SPEED LIMIT rectangle (MUTCD R2-1) instead of the red disc, and their numbers, every 5 from 15 to 80 (15 20 25 … 75 80) and **?**. A number chosen there is stored as written, in mph: `sign_value` and `value_kph` are the digits (25 mph is 25, never 40) and `sign_unit` is `mph`, nothing converted; the label on the photo says "35 mph". The keys take two digits: **3 5** is 35, **6 5** is 65; one digit alone, after a pause, is its tens (**3** is 30), and **0** is **?**. Everywhere else nothing changes: red discs of km/h, one key per speed.

### A limit with hours (Panel below: Hours)

A 30 with a plate of hours under it is another sign for the classifier: "Speed limit 30, with hours", the class `maximum_speed_hours:30`. In **Sign review** choose **Speed limit**, its number and **Panel below › Hours**, and draw one box around the disc and the plate; the page says so under the row. When the plate can be read, set **From** and **To** under it: whole hours, saved with the sign, and the class becomes `maximum_speed_hours:30:22-6`, so that the car and the brain know them. Leave them empty for a plate too small to read, or one with days, minutes or two ranges. Hours with fewer than 3 crops of train stay in `maximum_speed_hours:30`. A limit with hours and no readable number stays a limit with no number. **Apply previous** carries such a box with its shape and its hours: a box of the disc alone it finds there is taken down over the plate, to check. A plain number that the cutter finds closer with **Hours** keeps **Hours**. **None** and **Other** keep the box on the disc.

To reach the car, in this order:

1. Mark the signs in **Sign review**.
2. **Import the sign reviews.**
3. **Train the cutter**: the car's classifier sees only the box SignNet cuts, so SignNet has to learn the tall box too. Choose it on **Models**: the classifier learns the false boxes of the cutter in use (Train › Pipeline does steps 2 to 4 in a row, with the new cutter).
4. **Train the classifier**: it gets one class for each number with hours, and one for each number with hours read. The hours need drives at full definition to be read on the car: at 1344 × 760 the plate is a blob.
5. On **Models** choose the classifier, then **Publish**. The brain reads the drives with the networks of the release, so a brain trained before this Publish has never seen the new class.
6. **Train the brain**: it reads the signs of its drives again first. Models › Brain then says **Reads them** under **Hours plates**, if frames of train with an answer of the speed had a plate, and **Reads them and their hours** if they had their hours read.
7. Choose a seed on **Models** and **Publish** again.

With no Hours label nothing changes: no such class, and the same classes as today.

### A limit for wet roads (Panel below: Wet)

An 80 with a plate saying it holds only on a wet road (the German "bei Nässe", or a cloud with rain) is another sign for the classifier: "Speed limit 80, when wet", the class `maximum_speed_wet:80`. In **Sign review** choose **Speed limit**, its number and **Panel below › Wet**, and draw one box around the disc and the plate, as for hours. The way to the car is the one of the hours, steps 1 to 5.

With no Wet label nothing changes: no such class, and the same classes as today.

The brain gets the plate as one more input, and sees in the picture whether the road is wet. Nothing else tells it: it has to learn what a wet road looks like, so it needs both passes.

- Pass the plate on a wet road at the number, your speed being the answer, and it learns to slow down there.
- Pass it on a dry road above the number, and it learns to go on.

Models › Brain then says **Reads them** under **Wet plates**. Publish refuses such a brain with a classifier that has no wet class.

### Drives at full definition

A comma with **Record road at full resolution** on (Developer tab) writes its `fcamera.hevc` at 2688 × 1520 instead of 1344 × 760. The server tells them apart by the size of the video when it extracts the frames, drive by drive, with no setting; old and new drives live side by side. Such a drive says **HD** beside its date.

- **Rows, boxes and labels stay in 1344 × 760 pixels**, on every drive. Each picture `frame_XXXXXXXX.png` is the recorded frame reduced by 2, and the recorded frame stays beside it as `frame_XXXXXXXX.full.jpg`. So the cutter, the reviews already saved and the dataset do not change.
- **Sign review** shows the recorded frame, in the photo, the zoom and the **Classifier** square. The drive player (Speed review, Models › Drive) plays it 1344 wide, the comma's usual frame, a quarter of the bytes, so the player seeks fast (a video made at 2688 before 7 Nov 2026 is made again).
- **Training** cuts the classifier's crops from the `.full.jpg` when a frame has one, by itself, and the crop cache is rebuilt for those frames (`meta.json` and the log say `full_frames`). Frames without one keep their crops. A classifier trained before those drives is not changed: training stays your choice.
- **What it costs:** about 4.5 GB an hour on the comma instead of 2.25, and on the server one more JPEG for each picture, with a preview of the full size. `deleter.py` removes the oldest segments when the comma has under 10 % or 5 GB free, so pull a full drive within days.

With either switch on the road camera goes through the BPS, the comma's other image processor, and that also changes the picture the driving model sees: another debayer, no vignetting correction, about 7 ms later. Both off, everything is as before. A change applies from the next drive.

The road through the BPS has not run on a comma yet: the code is read and compiled, the picture is not seen. So the first time, turn a switch on with the car parked and the ignition on for a few minutes, download that drive from the **comma** pill and look at it in Sign review: right colours, no seams down the picture. Only then drive with it.

### The car's networks on a frame (T)

In Sign review on a computer, the short bar between the photo and the bar under it is a grip: drag it up and the photo gets lower, the timeline under it gets the room; drag it down and it grows back, at most to the width of the column. With the grip focused, ↑ and ↓ move it (⇧ in bigger steps); a double click goes back to the default height. The browser remembers the height. The bar under the photo has two rows: the frame (‹ ›), the filters and **Car networks** / **Ask AI** on the first; the frame's state, the frame data and **+ Box** / **Delete** on the second. On a tablet or a phone the page scrolls instead and there is no grip.

In Sign review, **Car networks** (key **T**, its button in the bar under the photo, next to **Ask AI**) shows what the car's own networks read on the frame on screen: SignNet (the cutter) finds the boxes and the classifier reads each one, run by the car's own code (`vision.read_signs` of the sunnypilot clone, `NNSLR_SUNNYPILOT_CLONE` or `/root/sunnypilot`) with the networks and the settings of the release the car runs (`models/speed_limits.json`). It works on any frame: a picture at 1 a second, a sign the comma read, or any frame of the video between them (← →). Once on, it reads every frame shown until its button (or **T**) is pressed again; the browser remembers the choice. On a frame not confirmed each box of the car goes straight into **Signs** on the right, with its kind, value and whom it is for, in fuchsia on the photo: fuchsia means found by the car's networks, and it stays fuchsia once confirmed. Their row says *car networks*. There is no button to press: check them and **Confirm** as always; nothing is saved before that, and a frame only passed over stays to review, without them. **Not a sign** boxes come too: most are false boxes of the cutter, and confirmed as they are they are examples of not a sign, so on a real sign change the kind, on a false box leave or delete it. A box deleted there does not come back while the page is open, and no box is added where the frame already has one. Whom a box is for (*OURS*) comes from the applicability network in use (Models tab), which is not on the car: it runs here on the CPU (`nnslr_tools._decider_worker`, in `.venv-gpu`, loaded at the first frame, about 4 s, then 0.1 s a frame, and gone after 10 idle minutes), with the car's speed at that frame. It answers on every box but those read as not a sign. It learnt only on the speed families (limits, ends, zones, variable displays, road markings), so on any other sign its answer is only a hint to check. If it cannot answer, a card under the bar says why and the reading stays good. On a confirmed frame the car's boxes are only drawn, in fuchsia (*car 1 · 80 · 97%*), and listed in that card with what the classifier read, how sure it is and what the car does with it: **Limit 80** (or **Ends the limit**) goes to the car's memory; **Road type** and **Board, road type** go to the road type; **No limit** is read sure enough but holds no limit (another sign, not a sign); **Dropped** is under the release's minimum confidence (70 % today), and the car ignores it. On the photo a dashed box gives nothing for the limit and a dotted one is dropped.

It is close to the car, not bit for bit: the car reads the camera's frame before the video encoder, with tinygrad on its GPU, while the server reads the recorded video (`fcamera.hevc`, decoded to the camera's NV12) with onnxruntime on its CPU, so a confidence near 70 % can fall on the other side. One frame is not a limit either: the car's memory takes a number read in 2 frames within 1.5 s. Only the camera, never the map. The first frame of a GOP takes about half a second (the server decodes its 20 frames), the next ones of the same GOP a few hundredths. A new release in the sunnypilot clone is used from the next frame read, without a restart; with no release there, the box says so (503).

### The AI reviewer (Settings)

A review can be done by hand, or by an AI that sees the images, through any server compatible with the OpenAI API (`/v1/models` and `/v1/chat/completions`): strata, your own llama.cpp `llama-server` on another machine with a vision model and its `--mmproj` file (for example Qwen3-VL-32B-Instruct), or another service.

- **Connecting a provider**: menu **Account → Settings**, the **AI reviewer** box: a name, an address that ends in `/v1`, the API key (when the server wants one) and the model (the list comes from the server; when it does not answer, type it by hand). **Test** sends a frame reviewed by a person, without the proposals, and says whether the model answers in JSON and reads the speed sign. When the server says the model takes text only, it says so without asking the model anything. Below, **Who reviews** is a list with a check mark: choose a provider that passed the Test, or **Don't use AI**. A provider never tested, or one that did not pass its last Test, cannot be chosen (not from the terminal either). When the chosen reviewer no longer passes it, **Ask AI** and **Review with AI** stay off, with the reason, until it passes again. Changing the address or the model clears the Test.
- **From the terminal**, for example strata:

  ```sh
  .venv/bin/nnslr llm-provider add --name strata --base-url https://strata.farm.14bodhi.com/v1 --key-file /root/.config/strata-api-key
  .venv/bin/nnslr llm-provider test strata
  .venv/bin/nnslr llm-provider use strata
  ```

  `nnslr llm-provider list` lists the providers (never the keys); then `models ID`, `remove ID`, `use none`. Without `--model` it takes the first model the server lists.
- **Where the key is**: in `data/web/private/llm-providers.json` (permissions 600, folder 700, outside git). `NNSLR_LLM_PROVIDERS=/full/path.json` moves the file. The key never leaves the server: no page, answer, log or report contains it, and the browser only knows that there is one. Leaving the key field empty keeps the saved key; **Remove key** removes it.
- **On the review page**: **Ask AI** (key **I**, in the bar under the photo, next to **Car networks**) shows the AI's suggestion for the frame in a card under the bar, with Keep, Correct, Add, Delete or Not judged for every box. It saves nothing: **Apply** turns it into changes to check, and your **Confirm** saves them as your review, as always; **Dismiss** throws it away. At most two requests to the AI run at a time. **Fit with AI** (**Shift+C**) fits the selected box, or every box of the frame when none is selected, with the same AI; **Fit box** does it without AI, **C** for every box of the frame (see [Fitting a box](#fitting-a-box-c-and-c)).
- **A whole route**: in the list of routes, **Review with AI** on the routes not finished (until an AI reviewer is chosen in Settings, there is a single **Set up AI review** link in its place, and the same link in place of **Ask AI** on the review page). **Try without saving** tries 20 frames without saving: the suggestions go to `data/ai_reviews/<route>/`, and the review page of the route shows them in the **AI reviewer** card under the photo of every frame tried (with **Apply** and **Dismiss**, like **Ask AI**) and in the **AI trial** filter. **Review and save** saves the AI's reviews, only with a provider that passed the Test. They still have to be confirmed (on the **AI · to confirm** page, in the list «N by AI to confirm»), and they go into training only after a person confirms them: the import leaves them out, and removes the ones imported before this rule. It starts as a job of the panel (`helpers/ai_review.sh`, followed in the Overview), never together with a preparation or an update. Frames confirmed by a person are never touched.
- **The reviews saved by the AI are final**: nobody approves them again, and the next import (`helpers/3_train.sh`, **Import sign reviews**) puts them into training as AI reviews: `reviewer` `ai/<provider>/<model>`, type `ai`, channel `web`, `label_basis` `ai_review`. Saving does not import and does not train.
- **Measuring a provider**: Evaluate → **AI reviewers**, **Measure** (`helpers/measure_ai_reviewer.sh`): up to 60 frames reviewed by people, always the same ones for every provider. It measures the speed signs found and read right, the agreement on the frames without signs, the false boxes, and the seconds per frame. It saves nothing; the result goes to `data/evaluations/ai_reviewers/`.
- **Who can**: only a browser that has signed in, or the site on 127.0.0.1, changes the providers and uses the AI. The token (API, MCP, agents) can only read the settings, the state of the AI and the measures ([API_MCP.md](API_MCP.md), section 8).

## 5. Common problems

| Message | What to do |
| --- | --- |
| `splitting the dataset needs at least 3 independent reviewed routes (or places)` | Prepare and review more routes, then run `helpers/3_train.sh` again. |
| `the GPU 0 is busy` / the button says "the GPU is busy with another process" or "both GPUs are busy: …" | Another job holds the card, or both cards (a training of ours, `openpilot.distill`, *a program the server cannot name*): wait for one to finish; the panel then starts on the card that is free. A cutter, classifier or decider training says it only when no card has 4 GB left beside trainings of those kinds and replays ([#41](https://github.com/cristianku/sunnypilot.speedlimits/issues/41)). From the terminal, `NNSLR_GPU_INDEX=1` runs on the other card (for `scripts/run_signnet.sh` with `CUDA_DEVICE_ORDER=PCI_BUS_ID` in front, which it does not set itself), and `helpers/3_train.sh --force` (`NNSLR_ALLOW_BUSY_GPU=1` for the scripts and the other helpers) starts anyway on a busy card, and both get slower. |
| `port 8765 is already in use` | A site is already on (the service, or another `nnslr review`): `helpers/2_review.sh` prints the link again, `helpers/2_review.sh --stop` stops the one started by hand. |
| `Sign-in required: reload the page and sign in` | The session ended (7 days without use, signed out, password changed): reload and sign in with name and password (section 3). |
| API or MCP: `401 unauthorized`, `501 mcp_unavailable`, `409 ...` | See [API_MCP.md](API_MCP.md), section 7. |
| `Sign in on the site to use the AI reviewer.` (403 `session_required`) | The AI reviewer works only from a browser that has signed in, or from the site on 127.0.0.1: the token can only read. |
| `Choose an AI reviewer in Settings.` (409 `no_ai_reviewer`) | Account → Settings → AI reviewer: add a provider, press **Test** and choose it in **Who reviews**; or `nnslr llm-provider test ID` and `nnslr llm-provider use ID`. |
| `... did not pass its last Test ...` / `Test ... in Settings first ...` (409 `ai_not_tested`) | The provider did not pass the Test (or was never tested): fix it and press **Test** in Settings (`nnslr llm-provider test ID`). Only then can it review. |
| 429 `ai_busy` | Two requests to the AI are already running: try again shortly. |
| 502 `ai_unreachable`, `ai_http_error`, 504 `ai_timeout` | The provider's server does not answer, refuses (a wrong key, a model that does not exist: the message says `HTTP <code>`) or does not answer within 2 minutes: check it with **Test**. |
| Test: `... takes text only: it cannot see the frames.` | The model cannot see images: choose a vision model (with llama.cpp, its `--mmproj` file is needed too). |
| `there are no stable weights on ... yet` | `--continue` needs a model already published as stable: train from scratch first. |
| A route stays at "videos to link" (`helpers/status.sh`) | `link-videos` found a conflict: see `data/logs/prepare/link-videos.json`. Segments with only the log and no `fcamera.hevc` (left by a fetch before 30 Oct 2026, or by Distill's) are not an error: they are not linked, and they are listed in `log_only`. |
| Extraction or pre-annotation failed | The reason is in `data/logs/prepare/<route>.log`. |
